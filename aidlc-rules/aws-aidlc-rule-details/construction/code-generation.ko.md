# 코드 생성 - 세부 단계

## 개요
이 단계에서는 두 개의 통합된 부분을 통해 각 작업 단위에 대한 코드를 생성합니다.
- **1부 - 계획**: 명시적인 단계를 통해 상세한 코드 생성 계획 수립
- **2부 - 생성**: 승인된 계획을 실행하여 코드, 테스트, 아티팩트 생성

**참고**: 브라운필드 프로젝트의 경우 "생성"은 중복 파일을 만드는 것이 아니라 적절한 경우 기존 파일을 수정하는 것을 의미합니다.

## 전제조건
- 해당 유닛에 대한 유닛 디자인 생성이 완료되어야 합니다.
- NFR 구현(실행된 경우)은 해당 장치에 대해 완료되어야 합니다.
- 모든 유닛 디자인 아티팩트를 사용할 수 있어야 합니다.
- 장치가 코드 생성 준비가 되었습니다.

# 1부: 계획

## 1단계: 단위 컨텍스트 분석
- [ ] Unit Design Generation의 유닛 디자인 아티팩트 읽기
- [ ] 할당된 스토리를 이해하기 위해 유닛 스토리 맵을 읽어보세요.
- [ ] 장치 종속성 및 인터페이스 식별
- [ ] 장치가 코드 생성 준비가 되었는지 확인

## 2단계: 상세한 단위 코드 생성 계획 수립
- [ ] `aidlc-docs/aidlc-state.md`에서 작업공간 루트 및 프로젝트 유형 읽기
- [ ] 코드 위치 결정(구조 패턴에 대한 중요 규칙 참조)
- [ ] **브라운필드에만 해당**: 수정할 기존 파일에 대한 리버스 엔지니어링 code-structure.md를 검토합니다.
- [ ] 정확한 경로를 문서화하세요(aidlc-docs/는 안 됨).
- [ ] 단위 생성을 위한 명시적인 단계를 만듭니다.
  - 프로젝트 구조 설정(그린필드에만 해당)
  - 비즈니스 로직 생성
  - 비즈니스 논리 단위 테스트
  - 비즈니스 로직 요약
  - API 레이어 생성
  - API 계층 단위 테스트
  - API 레이어 요약
  - 리포지토리 계층 생성
  - 리포지토리 계층 단위 테스트
  - 저장소 계층 요약
  - 프런트엔드 구성요소 생성(해당되는 경우)
  - 프런트엔드 구성 요소 단위 테스트(해당하는 경우)
  - 프런트엔드 구성 요소 요약(해당되는 경우)
  - 데이터베이스 마이그레이션 스크립트(데이터 모델이 있는 경우)
  - 문서 생성(API 문서, README 업데이트)
  - 배포 아티팩트 생성
- [ ] 각 단계에 순차적으로 번호를 매깁니다.
- [ ] 스토리 매핑 참조 포함
- [ ] 각 단계에 체크박스 추가 [ ]

## 3단계: 단위 생성 컨텍스트 포함
- [ ] 이 장치에는 다음이 포함됩니다.
  - 본 기기에서 구현한 스토리
  - 다른 단위/서비스에 대한 종속성
  - 예상되는 인터페이스 및 계약
  - 이 단위가 소유한 데이터베이스 엔터티
  - 서비스 경계 및 책임

## 4단계: 단위 계획 문서 작성
- [ ] 전체 계획을 `aidlc-docs/construction/plans/{unit-name}-code-generation-plan.md`로 저장
- [ ] 단계 번호 포함(1단계, 2단계 등)
- [ ] 단위 컨텍스트 및 종속성 포함
- [ ] 스토리 추적성 포함
- [ ] 계획이 단계별로 실행 가능하도록 보장
- [ ] 이 계획이 코드 생성을 위한 단일 정보 소스임을 강조합니다.

## 5단계: 단위 계획 요약
- [ ] 사용자에게 단위코드 생성계획 요약 제공
- [ ] 하이라이트 단위 생성 방식
- [ ] 단계 순서 및 스토리 범위를 설명합니다.
- [ ] 총 단계 수 및 예상 범위 참고

## 6단계: 승인 프롬프트 로그
- [ ] 승인을 요청하기 전에 `aidlc-docs/audit.md`에 타임스탬프가 포함된 프롬프트를 기록하세요.
- [ ] 전체 단위 코드 생성 계획에 대한 참조 포함
- [ ] ISO 8601 타임스탬프 형식 사용

## 7단계: 명시적인 승인을 기다립니다.
- [ ] 사용자가 단위 코드 생성 계획을 명시적으로 승인할 때까지 진행하지 마십시오.
- [ ] 승인은 전체 계획 및 생성 순서를 포괄해야 합니다.
- [ ] 사용자가 변경을 요청하면 계획을 업데이트하고 승인 프로세스를 반복합니다.

## 8단계: 승인 응답 기록
- [ ] `aidlc-docs/audit.md`의 타임스탬프와 함께 사용자 승인 응답을 기록합니다.
- [ ] 정확한 사용자 응답 텍스트를 포함하세요.
- [ ] 승인 상태를 명확하게 표시

## 9단계: 업데이트 진행 상황
- [ ] 마크 코드 생성 1부(계획)가 `aidlc-state.md`에 완료됨
- [ ] "현재 상태" 섹션 업데이트
- [ ] 코드 생성으로의 전환 준비

# 2부: 세대

## 10단계: 로드 단위 코드 생성 계획
- [ ] `aidlc-docs/construction/plans/{unit-name}-code-generation-plan.md`의 전체 계획 읽기
- [ ] 완료되지 않은 다음 단계 식별(첫 번째 [ ] 확인란)
- [ ] 해당 단계에 대한 컨텍스트 로드(단위, 종속성, 스토리)

## 11단계: 현재 단계 실행
- [ ] 계획에서 대상 디렉토리 확인(aidlc-docs/는 아님)
- [ ] **브라운필드만 해당**: 대상 파일이 존재하는지 확인
- [ ] 현재 단계에서 설명하는 내용을 정확하게 생성합니다.
  - **파일이 존재하는 경우**: 그 자리에서 수정합니다(`ClassName_modified.java`, `ClassName_new.java` 등을 생성하지 마세요).
  - **파일이 존재하지 않는 경우**: 새 파일 만들기
- [ ] 올바른 위치에 쓰기:
  - **애플리케이션 코드**: 프로젝트 구조별 작업공간 루트
  - **문서**: `aidlc-docs/construction/{unit-name}/code/`(마크다운만 해당)
  - **빌드/구성 파일**: 작업공간 루트
- [ ] 유닛 스토리 요구 사항 따르기
- [ ] 종속성 및 인터페이스 존중

## 12단계: 업데이트 진행 상황
- [ ] 유닛코드 생성 계획에서 완료된 단계를 [x]로 표시합니다.
- [ ] 생성이 완료되면 관련 유닛 스토리를 [x]로 표시합니다.
- [ ] `aidlc-docs/aidlc-state.md` 현재 상태 업데이트
- [ ] **브라운필드에만 해당**: 중복된 파일이 생성되지 않았는지 확인합니다(예: `ClassName.java`과 함께 `ClassName_modified.java`이 없음).
- [ ] 생성된 모든 아티팩트 저장

## 13단계: 생성 계속 또는 완료
- [ ] 더 많은 단계가 남아 있으면 10단계로 돌아갑니다.
- [ ] 모든 단계가 완료되면 완료 메시지 표시로 진행합니다.

## 14단계: 완료 메시지 표시
- 다음 구조에 완료 메시지가 표시됩니다.
     1. **완료 알림**(필수): 항상 다음으로 시작하세요.

```markdown
# 💻 Code Generation Complete - [unit-name]
```

     2. **AI 요약**(선택사항): 구조화된 주요 항목 요약 제공
        - **브라운필드**: 수정된 파일과 생성된 파일을 구별합니다(예: "• 수정됨: `src/services/user-service.ts`", "• 생성됨: `src/services/auth-service.ts`")
        - **그린필드**: 생성된 파일을 경로와 함께 나열합니다(예: "• 생성됨: `src/services/user-service.ts`")
        - 경로와 함께 테스트, 문서, 배포 아티팩트 나열
        - 사실을 유지하고 워크플로 지침이 없음
     3. **형식화된 워크플로 메시지**(필수): 항상 다음과 같은 정확한 형식으로 끝납니다.

```markdown
> **📋 <u>**REVIEW REQUIRED:**</u>**  
> Please examine the generated code at:
> - **Application Code**: `[actual-workspace-path]`
> - **Documentation**: `aidlc-docs/construction/[unit-name]/code/`



> **🚀 <u>**WHAT'S NEXT?**</u>**
>
> **You may:**
>
> 🔧 **Request Changes** - Ask for modifications to the generated code based on your review  
> ✅ **Continue to Next Stage** - Approve code generation and proceed to **[next-unit/Build & Test]**

---
```

## 15단계: 명시적 승인을 기다립니다.
- 사용자가 생성된 코드를 명시적으로 승인할 때까지 진행하지 마세요.
- 승인은 명확하고 모호하지 않아야 합니다.
- 사용자가 변경을 요청하면 코드를 업데이트하고 승인 프로세스를 반복하세요.

## 16단계: 승인 및 업데이트 진행 상황 기록
- 타임스탬프가 포함된 audit.md의 로그 승인
- 타임스탬프와 함께 사용자의 승인 응답을 기록합니다.
- aidlc-state.md에서 이 단위에 대한 코드 생성 단계를 완료로 표시합니다.

## 중요한 규칙

### 코드 위치 규칙
- **애플리케이션 코드**: 작업공간 루트만 해당(aidlc-docs/는 절대 안 됨)
- **문서**:aidlc-docs/ 전용(마크다운 요약)
- 코드를 생성하기 전에aidlc-state.md에서 **작업공간 루트**를 읽으세요.

**프로젝트 유형별 구조 패턴**:
- **브라운필드**: 기존 구조 사용(예: `src/main/java/`, `lib/`, `pkg/`)
- **그린필드 단일 장치**: 작업공간 루트의 `src/`, `tests/`, `config/`
- **그린필드 다중 단위(마이크로서비스)**: `{unit-name}/src/`, `{unit-name}/tests/`
- **그린필드 다중 장치(모놀리스)**: `src/{unit-name}/`, `tests/{unit-name}/`

### 브라운필드 파일 수정 규칙
- 생성하기 전에 파일이 존재하는지 확인하십시오.
- 존재하는 경우: 내부 수정(`ClassName_modified.java`과 같은 복사본을 생성하지 않음)
- 존재하지 않는 경우: 새 파일 만들기
- 생성 후 중복 파일이 없는지 확인(12단계)

### 계획 단계 규칙
- 모든 생성 활동에 대해 명시적이고 번호가 매겨진 단계를 만듭니다.
- 계획에 스토리 추적성을 포함합니다.
- 문서 단위 컨텍스트 및 종속성
- 생성 전에 명시적인 사용자 승인 받기

### 생성 단계 규칙
- **하드코딩된 논리 없음**: 단위 계획에 작성된 것만 실행합니다.
- **계획을 정확하게 따르세요**: 단계 순서에서 벗어나지 마세요.
- **체크박스 업데이트**: 각 단계를 완료한 후 즉시 [x]를 표시하세요.
- **스토리 추적성**: 기능이 구현되면 유닛 스토리 [x]를 표시합니다.
- **RESPECT DEPENDENCIES**: 단위 종속성이 충족되는 경우에만 구현

### 자동화 친화적인 코드 규칙
UI 코드(웹, 모바일, 데스크톱)를 생성할 때 요소가 자동화 친화적인지 확인하세요.
- 대화형 요소(버튼, 입력, 링크, 양식)에 `data-testid` 속성 ​​추가
- 일관된 이름 사용: `{component}-{element-role}`(예: `login-form-submit-button`, `user-list-search-input`)
- 렌더링 간에 변경되는 동적 또는 자동 생성 ID를 피하세요.
- 코드 변경 시 `data-testid` 값을 안정적으로 유지합니다(요소 목적이 변경되는 경우에만 변경).

## 수료기준
- 완전한 단위 코드 생성 계획이 작성 및 승인되었습니다.
- [x]로 표시된 단위 코드 생성 계획의 모든 단계
- 계획대로 구현된 모든 유닛 스토리
- 생성된 모든 코드 및 테스트(테스트는 빌드 및 테스트 단계에서 실행됨)
- 생성된 배포 아티팩트
- 빌드 및 검증 준비가 완료된 전체 장치
