# 기능적 디자인

## 목적
**단위별 상세한 비즈니스 로직 설계**

기능적 디자인은 다음에 중점을 둡니다.
- 장치에 대한 자세한 비즈니스 로직 및 알고리즘
- 엔터티와 관계가 포함된 도메인 모델
- 상세한 비즈니스 규칙, 검증 논리 및 제약 조건
- 기술에 구애받지 않는 설계(인프라 문제 없음)

**참고**: 이는 애플리케이션 디자인(INCEPTION 단계)의 상위 수준 구성 요소 디자인을 기반으로 합니다.

## 전제조건
- 단위 생성이 완료되어야 합니다.
- 작업 단위(UOW) 아티팩트를 사용할 수 있어야 합니다.
- 애플리케이션 디자인 권장(상위 수준 구성 요소 구조 제공)
- 실행 계획은 기능적 설계 단계가 실행되어야 함을 나타내야 합니다.

## 개요
기술에 구애받지 않고 순전히 비즈니스 기능에만 초점을 맞춘 장치에 대한 상세한 비즈니스 로직을 설계합니다.

## 실행 단계

### 1단계: 단위 컨텍스트 분석
- `aidlc-docs/inception/application-design/unit-of-work.md`에서 단위 정의 읽기
- `aidlc-docs/inception/application-design/unit-of-work-story-map.md`에서 할당된 스토리 읽기
- 단위 책임 및 경계 이해

### 2단계: 기능적 디자인 계획 수립
- 기능적 디자인을 위한 체크박스[]를 사용하여 계획 생성
- 비즈니스 로직, 도메인 모델, 비즈니스 규칙에 중점을 둡니다.
- 각 단계에는 체크박스 []가 있어야 합니다.

### 3단계: 상황에 맞는 질문 생성
**지침**: 단위 정의와 기능적 디자인 아티팩트를 철저하게 분석하여 설명을 통해 기능적 디자인을 개선할 수 있는 모든 영역을 식별합니다. 포괄적인 이해를 보장하기 위해 적극적으로 질문하십시오.

**중요**: 기능적 디자인 품질에 영향을 미칠 수 있는 모호하거나 세부 사항이 누락된 경우 기본적으로 질문을 합니다. 잘못된 가정을 하는 것보다 너무 많은 질문을 하는 것이 좋습니다.

- [답변]을 사용한 질문 삽입: 태그 형식
- 모호함, 누락된 정보 또는 설명이 필요한 영역에 중점을 둡니다.
- 사용자 입력이 기능적 설계 결정을 향상시킬 수 있는 모든 곳에 질문을 생성하세요.
- **의심스러운 경우 질문하세요** - 과신은 잘못된 디자인으로 이어집니다.

**고려할 질문 카테고리**(모든 카테고리 평가):
- **비즈니스 로직 모델링** - 핵심 엔터티, 워크플로, 데이터 변환 및 비즈니스 프로세스에 대해 질문
- **도메인 모델** - 도메인 개념, 엔터티 관계, 데이터 구조 및 비즈니스 객체에 대해 질문하세요.
- **비즈니스 규칙** - 의사 결정 규칙, 검증 논리, 제약 조건, 비즈니스 정책에 대해 질문하세요.
- **데이터 흐름** - 데이터 입력, 출력, 변환 및 지속성 요구 사항에 대해 문의하세요.
- **통합 지점** - 외부 시스템 상호 작용, API 및 데이터 교환에 대해 문의하세요.
- **오류 처리** - 오류 시나리오, 유효성 검사 실패 및 예외 처리에 대해 문의하세요.
- **비즈니스 시나리오** - 극단적인 사례, 대체 흐름, 복잡한 비즈니스 상황에 대해 질문하세요.
- **프런트엔드 구성 요소**(해당하는 경우) - UI 구성 요소 구조, 사용자 상호 작용, 상태 관리 및 양식 처리에 대해 문의하세요.

### 4단계: 매장 계획
- `aidlc-docs/construction/plans/{unit-name}-functional-design-plan.md`로 저장
- 모든 [답변]: 사용자 입력용 태그 포함

### 5단계: 답변 수집 및 분석
- 사용자가 모든 [답변]: 태그를 완료할 때까지 기다립니다.
- **필수**: 모호하거나 모호한 답변이 있는지 모든 답변을 주의 깊게 검토하세요.
- **중요**: 불분명한 답변에 대해 후속 질문을 추가하세요. 모호한 답변으로 진행하지 마세요.
- "의존적임", "아마도", "확실하지 않음", "~이 혼합되어 있음", "어느 정도"와 같은 응답을 찾아보세요.
- 모호성이 발견되면 설명 질문 파일을 만듭니다.
- **모든 모호성이 해결될 때까지 진행하지 마세요**

### 6단계: 기능적 디자인 아티팩트 생성
- `aidlc-docs/construction/{unit-name}/functional-design/business-logic-model.md` 만들기
- `aidlc-docs/construction/{unit-name}/functional-design/business-rules.md` 만들기
- `aidlc-docs/construction/{unit-name}/functional-design/domain-entities.md` 만들기
- 단위에 프런트엔드/UI가 포함된 경우: `aidlc-docs/construction/{unit-name}/functional-design/frontend-components.md` 생성
  - 구성 요소 계층 구조 및 구조
  - 각 구성 요소에 대한 Props 및 상태 정의
  - 사용자 상호작용 흐름
  - 양식 유효성 검사 규칙
  - API 통합 지점(각 구성요소가 사용하는 백엔드 엔드포인트)

### 7단계: 완료 메시지 표시
- 다음 구조에 완료 메시지가 표시됩니다.
     1. **완료 알림**(필수): 항상 다음으로 시작하세요.

```markdown
# 🔧 Functional Design Complete - [unit-name]
```

     2. **AI 요약**(선택 사항): 기능적 설계에 대한 구조화된 핵심 요약 제공
        - 형식: "기능적 디자인이 [설명]을(를) 생성했습니다:"
        - 주요 비즈니스 논리 모델 및 엔터티 나열(글머리 기호)
        - 정의된 비즈니스 규칙 및 유효성 검사 논리 나열
        - 도메인 모델 구조 및 관계 언급
        - 워크플로 지침을 포함하지 마세요("검토해 주세요", "알려주세요", "다음 단계로 진행하세요", "진행하기 전에").
        - 사실에 기반하고 내용 중심을 유지하세요.
     3. **형식화된 워크플로 메시지**(필수): 항상 다음과 같은 정확한 형식으로 끝납니다.

```markdown
> **📋 <u>**REVIEW REQUIRED:**</u>**  
> Please examine the functional design artifacts at: `aidlc-docs/construction/[unit-name]/functional-design/`



> **🚀 <u>**WHAT'S NEXT?**</u>**
>
> **You may:**
>
> 🔧 **Request Changes** - Ask for modifications to the functional design based on your review  
> ✅ **Continue to Next Stage** - Approve functional design and proceed to **[next-stage-name]**

---
```

### 8단계: 명시적인 승인을 기다립니다.
- 사용자가 기능적 디자인을 명시적으로 승인할 때까지 진행하지 마세요.
- 승인은 명확하고 모호하지 않아야 합니다.
- 사용자가 변경을 요청하면 설계를 업데이트하고 승인 프로세스를 반복합니다.

### 9단계: 승인 및 업데이트 진행 상황 기록
- 타임스탬프가 포함된 audit.md의 로그 승인
- 타임스탬프와 함께 사용자의 승인 응답을 기록합니다.
- aidlc-state.md에서 기능적 디자인 단계 완료 표시
