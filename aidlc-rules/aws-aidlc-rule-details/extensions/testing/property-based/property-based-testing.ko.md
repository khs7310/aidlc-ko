# 속성 기반 테스트 규칙

## 개요

이러한 PBT(속성 기반 테스트) 규칙은 적용 가능한 AI-DLC 단계에 걸쳐 적용되는 교차 제약 조건입니다. 이는 식별 가능한 속성이 있는 코드가 속성 기반 기술을 사용하여 테스트되어 기존 예제 기반 테스트를 보완(교체하지 않음)하도록 보장합니다.

속성 기반 테스트는 모든 유효한 입력에 대해 유지되어야 하는 불변성을 정의한 다음 프레임워크를 사용하여 무작위 입력을 생성하고 반례를 검색합니다. 오류가 발견되면 프레임워크는 입력을 최소 재생 사례로 축소합니다. 이 접근 방식은 예제 기반 테스트에서 일반적으로 놓치는 극단적인 사례와 미묘한 버그를 찾아냅니다.

**시행**: 적용 가능한 각 단계에서 모델은 사용자에게 단계 완료 메시지를 표시하기 전에 이러한 규칙을 준수하는지 확인해야 합니다.

### PBT 찾기 동작 차단

**PBT 차단 결과**는 다음을 의미합니다.
1. 결과는 PBT 규칙 ID 및 설명과 함께 "PBT 결과" 섹션 아래의 단계 완료 메시지에 나열되어야 합니다.
2. 모든 차단 결과가 해결될 때까지 단계에서 "다음 단계로 계속" 옵션을 표시해서는 안 됩니다.
3. 모델은 변경해야 할 사항에 대한 명확한 설명과 함께 "변경 요청" 옵션만 제시해야 합니다.
4. 결과는 PBT 규칙 ID, 설명 및 단계 컨텍스트와 함께 `aidlc-docs/audit.md`에 기록되어야 합니다.

PBT 규칙이 현재 프로젝트 또는 단위에 적용 가능하지 않은 경우(예: 상태 저장 구성 요소가 없는 경우 PBT-06) 규정 준수 요약에서 **N/A**로 표시합니다. 이는 차단 결과가 아닙니다.

### 기본 시행

이 문서의 모든 규칙은 기본적으로 **차단**됩니다. 규칙의 확인 기준이 충족되지 않으면 차단 PBT 결과입니다. 위에 정의된 차단 결과 동작을 따르세요.

### 부분 시행 모드

사용자가 선택 중에 **부분** 시행을 선택한 경우 규칙 PBT-02, PBT-03, PBT-07, PBT-08 및 PBT-09만 시행됩니다. 다른 모든 규칙은 권고(비차단)로 처리됩니다. `## Extension Configuration` 아래의 `aidlc-docs/aidlc-state.md`에 적용 모드를 기록합니다.

### 검증기준 형식

이 문서의 검증 항목은 규정 준수 검사를 설명하는 간단한 항목입니다. 각 항목은 검토 중에 준수 또는 비준수로 평가되어야 합니다.

## 규칙 PBT-01: 설계 중 속성 식별

**규칙**: 비즈니스 로직, 데이터 변환 또는 알고리즘 작업을 포함하는 모든 단위는 기능 설계 단계에서 테스트 가능한 속성을 분석해야 합니다. 분석에서는 다음 속성 범주 중 어느 것이 적용되는지 식별해야 합니다.

|범주|설명|예|
|---|---|---|
|왕복|역수와 쌍을 이루는 연산은 원래 값을 산출합니다.|직렬화 → 역직렬화 = ID|
|불변|변환은 일부 측정 가능한 특성을 유지합니다.|sort는 컬렉션 크기와 요소를 유지합니다.|
|멱등성|작업을 두 번 적용하면 한 번과 동일한 결과가 생성됩니다.|dedup(dedup(목록)) = dedup(목록)|
|교환성|다른 작업 순서는 동일한 결과를 생성합니다.|추가(a, b) = 추가(b, a)|
|신탁|참조 구현 또는 단순화된 모델을 통해 결과를 확인할 수 있습니다.|최적화된 알고리즘과 무차별 대입|
|유도|더 작은 입력에 대해 입증된 속성이 더 큰 입력으로 확장됩니다.|재귀 구조, 분할 정복|
|간편한 검증|결과를 계산하기는 어렵지만 확인하기는 쉽습니다.|미로 해결사 출력을 확인하기 위해 걸어갈 수 있습니다.|

식별된 속성은 장치의 기능 설계 결과물에 문서화되어야 하며 PBT 테스트 요구 사항으로 코드 생성에 전달되어야 합니다.

**확인**:
- 기능적 디자인 아티팩트는 구성 요소별로 식별된 속성을 나열하는 "테스트 가능한 속성" 섹션을 포함합니다.
- 식별된 각 부동산은 위 카테고리 중 하나를 참조합니다.
- 식별 가능한 속성이 없는 구성 요소는 간략한 근거와 함께 "식별된 PBT 속성 없음"으로 명시적으로 표시됩니다.
- 코드 생성 계획 중에 속성 목록이 참조됩니다.

## 규칙 PBT-02: 왕복 속성

**규칙**: 논리 역이 있는 모든 연산에는 왕복을 확인하는 속성 기반 테스트가 있어야 합니다. 여기에는 다음이 포함되지만 이에 국한되지는 않습니다.
- 직렬화/역직렬화(JSON, XML, Protobuf, 바이너리 형식)
- 인코딩/디코딩(Base64, URL 인코딩, 압축)
- 구문 분석/형식 지정(날짜 구문 분석, 숫자 형식 지정, 구조화된 입력을 사용한 템플릿 렌더링)
- 암호화/복호화(키가 사용 가능한 경우)
- 데이터베이스 쓰기/읽기(I/O 자체가 아닌 데이터 변환 계층의 경우)
- 모든 유효한 `x`에 대해 `f_inverse(f(x)) = x`인 함수 쌍

속성 기반 테스트는 도메인에 적합한 생성기(PBT-07 참조)를 사용하여 임의의 유효한 입력을 생성해야 하며 왕복이 원래 입력과 동일한 값을 생성한다고 주장해야 합니다.

**확인**:
- 모든 직렬화/역직렬화 쌍에는 왕복 속성 테스트가 있습니다.
- 모든 인코딩/디코딩 쌍에는 왕복 속성 테스트가 있습니다.
- 모든 구문 분석/형식화 쌍에는 왕복 속성 테스트(또는 변환이 손실되는 이유를 문서화)가 있습니다.
- 왕복 테스트는 하드코딩된 예제가 아닌 생성된 입력을 사용합니다.
- 손실이 있는 변환(예: 정밀도 손실이 있는 부동 형식)은 허용 가능한 편차를 문서화하고 허용 오차 범위 내에서 테스트합니다.

## 규칙 PBT-03: 불변 속성

**규칙**: 문서화된 불변성이 있는 함수에는 생성된 입력 전체에 걸쳐 해당 불변성이 유지되는지 확인하는 속성 기반 테스트가 있어야 합니다. 일반적인 불변성은 다음과 같습니다:
- **크기 보존**: 출력 컬렉션의 크기는 입력과 동일합니다(예: 맵, 정렬).
- **요소 보존**: 출력에는 입력과 정확히 동일한 요소가 포함되며 재정렬될 수 있습니다(예: 정렬, 셔플)
- **순서 보장**: 출력이 순서 제약 조건을 충족합니다(예: 정렬은 비감소 순서 생성).
- **범위 제약**: 출력 값은 정의된 범위 내에 속합니다(예: 정규화는 [0, 1]의 값을 생성함)
- **유형 보존**: 출력 유형이 모든 유효한 입력에 대해 예상 유형과 일치합니다.
- **비즈니스 규칙 불변**: 항상 유지되어야 하는 도메인별 규칙(예: "유효한 거래 후에 계정 잔액이 절대로 마이너스가 되지 않습니다", "할인이 품목 가격을 초과하지 않습니다")

**확인**:
- 문서화된 각 불변에는 해당 속성 기반 테스트가 있습니다.
- 불변 테스트는 경계값을 포함한 광범위한 입력을 생성합니다.
- 기능적 디자인에서 식별된 비즈니스 규칙 불변성은 PBT에서 다룹니다.
- 불변 테스트는 예제 기반 테스트의 정확한 주장을 복제하지 않습니다. 특정 사례가 아닌 일반적인 규칙을 테스트합니다.

## 규칙 PBT-04: 멱등성 속성

**규칙**: 멱등성을 주장하거나 요구하는 모든 작업에는 이를 증명하는 속성 기반 테스트가 있어야 합니다. 테스트에서는 생성된 모든 유효한 입력에 대해 `f(f(x)) = f(x)`인지 확인해야 합니다. 이는 다음에 적용됩니다:
- 멱등성(PUT, DELETE)으로 문서화된 API 엔드포인트
- 데이터 정규화 또는 삭제 기능
- 캐시 채우기 작업
- 중복 제거 논리
- 구성 애플리케이션(구성을 두 번 적용해도 상태가 변경되지 않아야 함)
- 최소 1회 전달 시스템의 메시지 처리

**확인**:
- 멱등성으로 문서화된 모든 작업에는 `f(f(x)) = f(x)`을 주장하는 PBT가 있습니다.
- 멱등성 테스트는 도메인에 적합한 생성기(기본 요소뿐만 아니라)를 사용합니다.
- 상태 저장 작업의 경우 테스트는 단일 적용과 반복 적용 후 관찰 가능한 상태 동등성을 확인합니다.

## 규칙 PBT-05: Oracle 및 모델 기반 테스트

**규칙**: 참조 구현, 단순화된 모델 또는 알려진 올바른 알고리즘이 존재하는 경우 속성 기반 테스트는 테스트 중인 시스템을 Oracle과 비교해야 합니다. 이는 다음에 적용됩니다:
- 알려진 무차별 대입 버전을 대체하는 최적화된 알고리즘
- 레거시 구현을 대체하는 리팩토링된 코드
- 순차 버전과 비교한 병렬/동시 구현
- 잘 알려진 알고리즘의 맞춤형 구현(정렬, 검색, 그래프 탐색)
- 참조 데이터베이스와 비교되는 새로운 쿼리 엔진

속성 기반 테스트는 임의의 유효한 입력을 생성해야 하며 테스트 중인 시스템이 생성된 모든 입력에 대해 오라클과 동일한 결과를 생성한다고 주장해야 합니다.

**확인**:
- 참조 구현이 존재하는 경우(또는 간단하게 작성할 수 있는 경우) Oracle PBT가 존재합니다.
- Oracle 테스트는 정상, 경계 및 적대적 사례를 포괄하는 다양한 입력을 생성합니다.
- 동등성은 정확하게 정의됩니다(정확한 동등성, 구조적 동등성 또는 문서화된 허용 오차).
- 오라클이 존재하지 않는 경우 이 규칙은 근거와 함께 N/A로 표시됩니다.

## 규칙 PBT-06: 상태 저장 속성 테스트

**규칙**: 변경 가능한 상태를 관리하는 구성 요소는 상태 저장 속성 테스트를 위해 평가되어야 합니다. 상태 저장 PBT는 시스템에 대해 임의의 명령(작업) 시퀀스를 생성하고 각 단계 후에 불변성이 유지되는지 확인합니다. 이는 다음에 적용됩니다:
- 인메모리 캐시 및 데이터 저장소
- 상태 머신 및 워크플로 엔진
- 대기열 및 버퍼 구현
- 세션 관리 시스템
- 장바구니, 주문 파이프라인 및 유사한 상태 저장 비즈니스 객체
- 작업 결과가 이전 작업에 따라 달라지는 모든 구성 요소

상태 저장 PBT는 다음을 수행해야 합니다.
- 테스트 중인 시스템을 반영하는 단순화된 모델(참조 상태) 정의
- 유효한 명령의 무작위 시퀀스 생성(추가, 제거, 업데이트, 쿼리 등)
- 실제 시스템과 모델 모두에 대해 각 명령을 실행합니다.
- 각 명령 후에 시스템과 모델 간에 관찰 가능한 상태 또는 쿼리 결과가 일치하는지 확인
- 빈 시퀀스를 포함하여 다양한 길이의 테스트 시퀀스

**확인**:
- 기능 설계에서 식별된 상태 저장 구성 요소에는 상태 저장 PBT가 있거나 적용할 수 없는 이유가 문서화되어 있습니다.
- 비교를 위해 단순화된 모델이 정의됩니다.
- 명령 생성기는 현실적인 매개변수 분포로 유효한 작업 시퀀스를 생성합니다.
- 불변성은 마지막뿐만 아니라 시퀀스의 각 명령 이후에 확인됩니다.
- 상태 저장 구성 요소가 없으면 이 규칙은 N/A로 표시됩니다.

## 규칙 PBT-07: 발전기 품질

**규칙**: 속성 기반 테스트는 기본 유형뿐만 아니라 현실적이고 구조화된 입력을 생성하는 도메인별 생성기를 사용해야 합니다. 부실한 생성기(예: 이메일 필드의 임의 문자열, 연령 필드의 무제한 정수)는 의미 없는 테스트 사례를 생성하고 실제 버그를 놓칩니다.

발전기 요구 사항:
- **도메인 유형**: 비즈니스 제약 조건(유효한 이메일 형식, 양수 금액, 유효한 날짜 범위)을 존중하는 도메인 개체(예: 사용자, 주문, 거래)에 대해 사용자 정의 생성기를 생성해야 합니다.
- **제약된 프리미티브**: 수치 생성기는 도메인에서 요구하는 현실적인 범위로 제한되어야 합니다.
- **구조화된 데이터**: 복잡한 입력(중첩 개체, 도메인 개체 목록)용 생성기는 구조적으로 유효한 데이터를 생성해야 합니다.
- **에지 케이스 포함**: 생성기는 일반 값과 ​​함께 경계 값(빈 컬렉션, 0, 최대값, 유니코드 문자열)을 포함하도록 구성되어야 합니다.
- **재사용성**: 도메인 생성기는 테스트 파일 전체에 중복되지 않고 재사용 가능한 테스트 유틸리티로 정의되어야 합니다.

**확인**:
- 어떤 PBT도 도메인 유형 매개변수에 대해 원시 기본 생성기(예: `st.integers()` 단독)만 사용하지 않습니다.
- PBT에 사용되는 도메인 개체에 대한 사용자 정의 생성기가 존재합니다.
- 생성기는 문서화된 비즈니스 제약 조건(예: 양수 금액, 유효한 형식)을 존중합니다.
- 생성기 정의는 여러 테스트가 동일한 도메인 유형을 공유하는 경우 중앙 집중화되고 재사용 가능합니다.

## 규칙 PBT-08: 축소 및 재현성

**규칙**: 모든 속성 기반 테스트는 축소 및 결정론적 재현성을 지원해야 합니다.

- **축소**: 속성이 실패하면 PBT 프레임워크는 자동으로 실패한 입력을 최소 재생 사례로 줄여야 합니다. 테스트는 문서화된 기술적 이유(예: 축소가 통합 테스트에서 외부 서비스 호출과 호환되지 않음)가 아닌 이상 프레임워크의 축소 메커니즘을 비활성화하거나 우회해서는 안 됩니다.
- **재현성**: 모든 PBT 실행은 시드 값을 통해 재현 가능해야 합니다. 정확한 실패 시나리오를 재생할 수 있도록 시드는 실패 시 기록되어야 합니다. CI 구성은 결정적 실행을 위해 고정 시드를 사용하거나 오류 후 재현을 위해 모든 실행에서 무작위 시드를 기록해야 합니다.
- **CI 통합**: PBT는 프로젝트의 CI 파이프라인에 포함되어야 합니다. 불안정한 PBT 실패(코드 변경 없이 재시도를 통과하는 테스트)는 억제하는 것이 아니라 조사해야 합니다.

**확인**:
- PBT 프레임워크 축소가 활성화되었습니다(재정의되거나 비활성화되지 않음).
- 실패 시 테스트 출력에는 시드 값과 축소된 최소 실패 입력이 포함됩니다.
- CI 구성은 모든 PBT 실행에 대한 시드를 기록하거나 고정 시드를 사용합니다.
- 문서화된 정당성 없이 PBT가 CI에서 제외되지 않습니다.
- 비정상적인 PBT 오류는 자동으로 재시도되지 않고 추적 및 조사됩니다.

## 규칙 PBT-09: 프레임워크 선택

**규칙**: 프로젝트는 기본 언어에 대해 적절한 속성 기반 테스트 프레임워크를 선택하고 구성해야 합니다. 프레임워크는 다음을 지원해야 합니다.
- 도메인 유형에 대한 맞춤형 생성기/전략
- 실패한 사례의 자동 축소
- 종자 기반 재현성
- 프로젝트의 기존 테스트 실행기와 통합

언어별 권장 프레임워크(일부):

|언어|뼈대|메모|
|---|---|---|
|파이썬|가설|성숙하고 우수한 축소, Django 통합|
|자바스크립트/타입스크립트|빠른 확인|Jest, Vitest, Mocha와 통합|
|자바|jqwik|JUnit 5 통합, 상태 저장 테스트 지원|
|코틀린|Kotest 속성 테스트|Kotest 프레임워크 통합|
|스칼라|스칼라체크|SBT 통합, 널리 채택됨|
|녹|소품|매크로 기반, 우수한 수축성|
|가다|빠른|가볍고 관용적인 Go|
|하스켈|퀵체크|원래의 PBT 프레임워크|

선택한 프레임워크는 기술 스택 결정에 문서화되고 프로젝트 종속성으로 포함되어야 합니다.

**확인**:
- PBT 프레임워크가 선택되어 기술 스택 결정에 문서화됩니다.
- 프레임워크는 프로젝트 종속성(package.json, pom.xml, 요구사항.txt 등)에 포함됩니다.
- 프레임워크는 맞춤형 생성기, 축소 및 시드 기반 재현성을 지원합니다.
- 프로젝트가 여러 언어를 사용하는 경우 PBT 적용 코드가 있는 각 언어에는 프레임워크가 선택되어 있습니다.

## 규칙 PBT-10: 보완적인 테스트 전략

**규칙**: 속성 기반 테스트는 예제 기반 테스트를 대체하는 것이 아니라 보완해야 합니다. 두 가지 접근 방식은 서로 다른 목적으로 사용됩니다.

- **예제 기반 테스트**: 명시적인 예상 값과 함께 특정 알려진 시나리오, 회귀 사례 및 비즈니스에 중요한 엣지 사례를 문서화합니다. 이는 구체적인 동작에 대한 실행 가능한 문서 역할을 합니다.
- **속성 기반 테스트**: 넓은 입력 공간에서 일반 불변성을 확인합니다. 그들은 알려지지 않은 엣지 케이스를 찾고 속성이 보편적으로 유지되는지 검증합니다.

요구사항:
- 사용자 스토리 또는 요구 사항에서 식별된 중요한 비즈니스 시나리오에는 PBT가 동일한 속성을 다루더라도 명시적인 예제 기반 테스트가 있어야 합니다.
- PBT는 비즈니스에 중요한 경로에 대한 유일한 테스트가 되어서는 안 됩니다. 최소한 하나의 예제 기반 테스트는 주요 시나리오에 대해 예상되는 동작을 파악해야 합니다.
- PBT가 실패한 사례를 발견하면 축소된 최소 예제를 영구적인 예제 기반 회귀 테스트로 추가해야 합니다.
- 테스트 문서는 예제 기반 테스트와 속성 기반 테스트를 명확하게 구분해야 합니다(별도의 테스트 파일, 테스트 클래스 또는 명확한 이름의 테스트 함수).

**확인**:
- 비즈니스에 중요한 경로에는 예제 기반 테스트와 속성 기반 테스트가 모두 있습니다.
- PBT는 중요한 기능에 대한 유일한 테스트 적용 범위로 사용되지 않습니다.
- 테스트 파일 또는 테스트 클래스는 PBT와 예제 기반 테스트를 명확하게 구분하거나 레이블을 지정합니다.
- PBT에서 발견된 오류에 대한 회귀 테스트는 영구적인 예제 기반 테스트로 캡처됩니다.

- 생성된 아티팩트에 대해 모든 PBT 규칙 검증 기준을 평가합니다.
- 각 규칙을 준수, 비준수 또는 해당 없음으로 나열하는 단계 완료 요약에 "PBT 준수" 섹션을 포함합니다.
- 규정을 준수하지 않는 규칙이 있는 경우 이는 차단 PBT 결과입니다. 개요에 정의된 차단 결과 동작을 따르세요.
- 설계 문서 및 테스트 지침에 PBT 규칙 참조 포함

## 부록: 속성 범주 빠른 참조

기능 설계(PBT-01) 중 속성을 식별하는 개발자 및 AI 모델의 경우:

|패턴 이름|정식 용어|테스트 모양|사용 시기|
|---|---|---|---|
|거기서 또 다시|반전 기능|`f_inv(f(x)) == x`|직렬화, 인코딩, 구문 분석|
|어떤 것들은 절대 변하지 않아|불변|`measure(f(x)) == measure(x)`|정렬, 매핑, 필터링, 변환|
|더 많은 것들이 변할수록, 그것들은 더 많이 동일하게 유지됩니다|멱등성|`f(f(x)) == f(x)`|정규화, 중복 제거, 캐시 쓰기|
|다른 길, 같은 목적지|교환성|`f(g(x)) == g(f(x))`|산술, 집합 연산, 독립 변환|
|작은 문제부터 먼저 해결하세요|구조적 유도|`x`의 부동산은 `x + element`의 부동산을 의미합니다.|재귀 구조, 목록, 트리|
|증명하기는 어렵고 검증하기는 쉽다|확인|`verify(solve(x)) == true`|솔버, 옵티마이저, 검색 알고리즘|
|테스트 오라클|참고 비교|`f(x) == oracle(x)`|최적화 vs 무차별 대입, 리팩터링 vs 레거시|
