# 기본 보안 규칙

## 개요
이러한 보안 규칙은 모든 AI-DLC 단계에 적용되는 필수 교차 제한 사항입니다. 이는 선택적 지침이 아닙니다. 질문 생성, 디자인 아티팩트 생성, 코드 생성 및 완료 메시지 표시 시 단계에서 반드시 적용해야 하는 엄격한 제약 조건입니다.

**시행**: 적용 가능한 각 단계에서 모델은 사용자에게 단계 완료 메시지를 표시하기 전에 이러한 규칙을 준수하는지 확인해야 합니다.

### 보안 검색 동작 차단
**보안 발견 항목 차단**은 다음을 의미합니다.
1. 조사 결과는 SECURITY 규칙 ID 및 설명과 함께 "보안 조사 결과" 섹션 아래의 단계 완료 메시지에 나열되어야 합니다.
2. 모든 차단 결과가 해결될 때까지 단계에서 "다음 단계로 계속" 옵션을 표시해서는 안 됩니다.
3. 모델은 변경해야 할 사항에 대한 명확한 설명과 함께 "변경 요청" 옵션만 제시해야 합니다.
4. 발견 항목은 SECURITY 규칙 ID, 설명 및 단계 컨텍스트와 함께 `aidlc-docs/audit.md`에 기록되어야 합니다.

SECURITY 규칙이 현재 프로젝트에 적용되지 않는 경우(예: 데이터 저장소가 없는 경우 SECURITY-01) 규정 준수 요약에서 해당 규칙을 **N/A**로 표시합니다. 이는 차단 결과가 아닙니다.

### 기본 시행
이 문서의 모든 규칙은 기본적으로 **차단**됩니다. 규칙의 확인 기준이 충족되지 않으면 이는 차단 보안 결과입니다. 위에 정의된 차단 결과 동작을 따르세요.

### 검증기준 형식
이 문서의 검증 항목은 규정 준수 검사를 설명하는 간단한 항목입니다. 이는 단계 계획 파일에 사용되는 `- [ ]` / `- [x]` 진행률 추적 확인란과 다릅니다. 각 항목은 검토 중에 준수 또는 비준수로 평가되어야 합니다.

## 규칙 SECURITY-01: 저장 및 전송 중 암호화

**규칙**: 모든 데이터 지속성 저장소(데이터베이스, 객체 스토리지, 파일 시스템, 캐시 또는 이에 상응하는 것)에는 다음이 있어야 합니다.
- 관리형 키 서비스 또는 고객 관리형 키를 사용하여 저장 시 암호화 활성화
- 전송 중 암호화 적용(스토어 내부 및 외부로의 모든 데이터 이동에 대해 TLS 1.2+)

**확인**:
- 암호화 구성 블록 없이는 스토리지 리소스가 정의되지 않습니다.
- 데이터베이스 연결 문자열이 암호화되지 않은 프로토콜을 사용하지 않습니다.
- 객체 스토리지는 미사용 암호화를 시행하고 정책을 통해 비 TLS 요청을 거부합니다.
- 데이터베이스 인스턴스에는 스토리지 암호화가 활성화되어 있으며 TLS 연결을 시행합니다.

## 규칙 SECURITY-02: 네트워크 중개자에 대한 액세스 로깅

**규칙**: 외부 트래픽을 처리하는 모든 네트워크 연결 중개자는 액세스 로깅을 활성화해야 합니다. 여기에는 다음이 포함됩니다.
- 로드 밸런서 → 영구 저장소에 대한 액세스 로그
- API 게이트웨이 → 중앙 로그 서비스에 대한 실행 로깅 및 액세스 로깅
- CDN 배포 → 표준 로깅 또는 실시간 로그

**확인**:
- 액세스 로깅이 활성화되지 않으면 로드 밸런서 리소스가 정의되지 않습니다.
- 액세스 로깅이 구성되지 않으면 API 게이트웨이 단계가 정의되지 않습니다.
- 로깅 구성 없이는 CDN 배포가 정의되지 않습니다.

## 규칙 SECURITY-03: 애플리케이션 수준 로깅

**규칙**: 배포된 모든 애플리케이션 구성 요소에는 구조화된 로깅 인프라가 포함되어야 합니다.
- 로깅 프레임워크를 구성해야 합니다.
- 로그 출력은 중앙 집중식 로그 서비스로 전달되어야 합니다.
- 로그에는 타임스탬프, 상관 관계/요청 ID, 로그 수준 및 메시지가 포함되어야 합니다.
- 민감한 데이터(비밀번호, 토큰, PII)는 로그 출력에 표시되어서는 안 됩니다.

**확인**:
- 모든 서비스/기능 진입점에는 구성된 로거가 포함됩니다.
- 프로덕션 코드에서 기본 로깅 메커니즘으로 사용되는 임시 로깅 문이 없습니다.
- 로그 구성은 출력을 중앙 집중식 로그 서비스로 라우팅합니다.
- 비밀, 토큰 또는 PII가 기록되지 않습니다.

## 규칙 SECURITY-04: 웹 애플리케이션용 HTTP 보안 헤더

**규칙**: 다음 HTTP 응답 헤더는 모든 HTML 제공 엔드포인트에 설정되어야 합니다.

|헤더|필수값|
|---|---|
|`Content-Security-Policy`|제한적인 정책 정의(최소: `default-src 'self'`)|
|`Strict-Transport-Security`|`max-age=31536000; includeSubDomains`|
|`X-Content-Type-Options`|`nosniff`|
|`X-Frame-Options`|`DENY`(또는 프레이밍이 필요한 경우 `SAMEORIGIN`)|
|`Referrer-Policy`|`strict-origin-when-cross-origin`|

**참고**: `X-XSS-Protection`은 최신 브라우저에서 더 이상 사용되지 않습니다. 대신 `Content-Security-Policy`을(를) 사용하세요.

**확인**:
- 미들웨어 또는 응답 인터셉터는 모든 필수 헤더를 설정합니다.
- CSP 정책은 문서화된 정당성 없이 `unsafe-inline` 또는 `unsafe-eval`을 사용하지 않습니다.
- HSTS 최대 기간은 31536000(1년) 이상입니다.

## 규칙 SECURITY-05: 모든 API 매개변수에 대한 입력 유효성 검사

**규칙**: 모든 API 엔드포인트(REST, GraphQL, gRPC, WebSocket)는 처리하기 전에 모든 입력 매개변수의 유효성을 검사해야 합니다. 검증에는 다음이 포함되어야 합니다.
- **유형 확인**: 예상치 못한 유형 거부
- **길이/크기 경계**: 문자열의 최대 길이, 배열 및 페이로드의 최대 크기를 적용합니다.
- **형식 확인**: 구조화된 입력(이메일, 날짜, ID)에 허용 목록(정규식 또는 스키마)을 사용합니다.
- **삭제**: XSS를 방지하기 위해 사용자 제공 문자열에서 HTML/스크립트 콘텐츠를 이스케이프하거나 거부합니다.
- **삽입 방지**: 모든 데이터베이스 작업에 매개변수화된 쿼리를 사용합니다(문자열 연결 불가).

**확인**:
- 모든 API 핸들러는 유효성 검사 라이브러리 또는 스키마를 사용합니다.
- 원시 사용자 입력은 SQL, NoSQL 또는 OS 명령에 연결되지 않습니다.
- 문자열 입력에는 명시적인 최대 길이 제약이 있습니다.
- 요청 본문 크기 제한은 프레임워크 또는 게이트웨이 수준에서 구성됩니다.

## 규칙 SECURITY-06: 최소 권한 액세스 정책

**규칙**: 모든 ID 및 액세스 관리 정책, 역할 또는 권한 경계는 최소 권한을 따라야 합니다.
- 특정 리소스 식별자 사용 — API가 리소스 수준 권한을 지원하지 않는 한 절대 와일드카드 리소스를 사용하지 마세요(예외 문서화).
- 특정 작업 사용 - 절대 와일드카드 작업을 사용하지 마세요.
- 가능한 경우 범위 조건
- 읽기 및 쓰기 권한을 별도의 정책 설명으로 분리

**확인**:
- 문서화된 예외 없이 와일드카드 작업이나 와일드카드 리소스를 포함하는 정책은 없습니다.
- 어떤 서비스 역할도 서비스가 실제로 호출하는 것보다 더 광범위한 권한을 갖지 않습니다.
- 가능한 경우 관리형 정책을 선호하여 인라인 정책을 피합니다.
- 모든 역할에는 특정 서비스 또는 계정 범위의 신뢰 정책이 있습니다.

---

## 규칙 SECURITY-07: 제한적인 네트워크 구성

**규칙**: 모든 네트워크 구성(보안 그룹, 네트워크 ACL, 경로 테이블)은 기본적으로 거부를 따라야 합니다.
- 방화벽 규칙: 애플리케이션에 필요한 특정 포트만 엽니다.
- 포트 80/443의 공용 로드 밸런서를 제외하고 소스 `0.0.0.0/0`의 인바운드 규칙 없음
- 명시적으로 정당화되지 않는 한 모든 포트에 `0.0.0.0/0`이 있는 아웃바운드 규칙이 없습니다.
- 프라이빗 서브넷에는 직접 인터넷 게이트웨이 경로가 있어서는 안 됩니다.
- 가능한 경우 클라우드 서비스 액세스를 위해 개인 끝점을 사용하십시오.

**확인**:
- 공용 로드 밸런서의 80/443 이외의 포트에서 인바운드 `0.0.0.0/0`을 허용하는 방화벽 규칙은 없습니다.
- 데이터베이스 및 애플리케이션 방화벽 규칙은 소스를 특정 CIDR 블록 또는 보안 그룹 참조로 제한합니다.
- 프라이빗 서브넷은 NAT 게이트웨이(인터넷 게이트웨이 아님)를 통해 라우팅됩니다.
- 개인 끝점은 트래픽이 많은 클라우드 서비스 호출에 사용됩니다.

## 규칙 SECURITY-08: 애플리케이션 수준 액세스 제어

**규칙**: 리소스에 액세스하거나 리소스를 변경하는 모든 애플리케이션 엔드포인트는 애플리케이션 계층에서 인증 확인을 시행해야 합니다.
- **기본적으로 거부**: 공개로 명시적으로 표시되지 않는 한 모든 경로/엔드포인트는 인증을 요구해야 합니다(MUST).
- **객체 수준 승인**: ID로 리소스를 참조하는 모든 요청은 요청하는 사용자/주 구성원이 해당 리소스를 소유하거나 해당 리소스에 액세스할 수 있는 권한이 있는지 확인해야 합니다(IDOR 방지).
- **기능 수준 승인**: 관리 또는 권한 있는 작업은 호출자의 역할/권한을 서버 측에서 확인해야 하며 클라이언트 측 숨김에 의존하지 마십시오.
- **CORS 정책**: 교차 출처 리소스 공유는 명시적으로 허용된 출처로 제한되어야 합니다. 인증된 엔드포인트에서는 `Access-Control-Allow-Origin: *`을 사용하지 마세요.
- **토큰 유효성 검사**: JWT 또는 세션 토큰은 모든 요청(서명, 만료, 대상, 발급자)에 대해 서버 측에서 유효성을 검사해야 합니다.

**확인**:
- 모든 컨트롤러/핸들러에는 인증 미들웨어 또는 가드가 적용되어 있습니다.
- 호출자의 소유권이나 권한을 확인하지 않고는 엔드포인트가 리소스 ID에 대한 데이터를 반환하지 않습니다.
- 관리자/권한 있는 경로에는 서버 측에서 명시적인 역할 확인이 적용됩니다.
- CORS 구성은 인증된 엔드포인트에서 와일드카드 원본을 사용하지 않습니다.
- 토큰 검증은 모든 요청(로그인 시뿐만 아니라)마다 서버 측에서 발생합니다.

## 규칙 SECURITY-09: 보안 강화 및 잘못된 구성 방지

**규칙**: 배포된 모든 구성 요소는 강화 기준을 따라야 합니다.
- **기본 자격 증명 없음**: 배포 전에 기본 사용자 이름/비밀번호를 변경하거나 비활성화해야 합니다.
- **최소 설치**: 사용하지 않는 기능, 프레임워크, 샘플 애플리케이션 및 문서 끝점을 제거하거나 비활성화합니다.
- **오류 처리**: 프로덕션 오류 응답은 스택 추적, 내부 경로, 프레임워크 버전 또는 데이터베이스 세부정보를 최종 사용자에게 노출해서는 안 됩니다.
- **디렉터리 목록**: 웹 서버는 디렉터리 목록을 비활성화해야 합니다.
- **클라우드 스토리지**: 클라우드 객체 스토리지는 명시적으로 요구되거나 문서화되지 않는 한 공개 액세스를 차단해야 합니다(MUST).
- **패치 관리**: 런타임 환경, 프레임워크 및 OS 이미지는 지원되는 최신 버전을 사용해야 합니다.

**확인**:
- 구성 파일, 환경 변수 또는 IaC 템플릿에 기본 자격 증명이 없습니다.
- 프로덕션의 오류 응답은 일반 메시지를 반환합니다(스택 추적 또는 내부 세부 정보 없음).
- 클라우드 객체 스토리지는 문서화된 예외가 존재하지 않는 한 공개 액세스가 차단됩니다.
- 샘플/데모 애플리케이션 또는 기본 페이지가 배포되지 않습니다.
- 프레임워크 및 런타임 버전이 최신 버전이며 지원됩니다.

## 규칙 보안-10: 소프트웨어 공급망 보안

**규칙**: 모든 프로젝트는 소프트웨어 공급망을 관리해야 합니다.
- **종속성 고정**: 모든 종속성은 정확한 버전이나 잠금 파일을 사용해야 합니다.
- **취약성 스캔**: 종속성 취약점 스캐너를 구성해야 합니다.
- **사용하지 않는 종속성 없음**: 적극적으로 사용되지 않는 패키지를 제거합니다.
- Error 504 (Server Error)!!1504.That’s an error.There was an error. Please try again later.That’s all we know.
- **SBOM**: 프로젝트는 프로덕션 배포를 위한 소프트웨어 BOM을 생성해야 합니다.
- **CI/CD 무결성**: 빌드 파이프라인은 고정된 도구 버전과 확인된 기본 이미지를 사용해야 합니다. 프로덕션 Dockerfile 또는 CI 구성에는 `latest` 태그가 없습니다.

**확인**:
- 잠금 파일이 존재하며 버전 제어를 위해 커밋되었습니다.
- 종속성 취약점 검색 단계는 CI/CD에 포함되어 있거나 빌드 지침에 문서화되어 있습니다.
- 사용되지 않거나 버려진 종속성은 포함되지 않습니다.
- Dockerfiles 및 CI 구성은 프로덕션에 `latest` 또는 고정되지 않은 이미지 태그를 사용하지 않습니다.
- 종속성은 공식 또는 검증된 레지스트리에서 제공됩니다.

## 규칙 보안-11: 보안 설계 원칙

**규칙**: 애플리케이션 설계에는 처음부터 보안이 포함되어야 합니다.
- **관심사 분리**: 보안에 중요한 로직(인증, 권한 부여, 결제 처리)은 코드베이스 전체에 분산되지 않고 전용 모듈로 격리되어야 합니다.
- **심층 방어**: 단일 제어가 유일한 방어선이 되어서는 안 됩니다. 즉 계층 제어(검증 + 인증 + 암호화)입니다.
- **속도 제한**: 공용 엔드포인트는 남용을 방지하기 위해 속도 제한 또는 제한을 구현해야 합니다.
- **비즈니스 로직 남용**: 디자인은 행복한 경로 시나리오뿐만 아니라 오용 사례도 고려해야 합니다.

**확인**:
- 보안에 중요한 논리는 전용 모듈 또는 서비스에 캡슐화됩니다.
- 공개 API에 비율 제한이 구성되어 있습니다.
- 설계 문서에서는 하나 이상의 오용/남용 시나리오를 다룹니다.

## 규칙 보안-12: 인증 및 자격 증명 관리

**규칙**: 사용자 인증을 사용하는 모든 애플리케이션은 다음을 구현해야 합니다.
- **비밀번호 정책**: 최소 8자, 위반된 비밀번호 목록 확인
- **자격증명 저장소**: 비밀번호는 적응형 알고리즘을 사용해 해시되어야 하며, 약하거나 비적응형 해싱은 절대 안 됩니다.
- **다단계 인증**: MFA는 관리 계정에 대해 지원되어야 하며 모든 사용자가 사용할 수 있어야 합니다.
- **세션 관리**: 세션은 서버 측 만료가 있어야 하고, 로그아웃 시 무효화되어야 하며 secure/httpOnly/sameSite 쿠키 속성을 사용해야 합니다.
- **무차별 대입 보호**: 로그인 엔드포인트는 반복된 실패 후 계정 잠금, 점진적 지연 또는 CAPTCHA를 구현해야 합니다.
- **하드코딩된 자격 증명 없음**: 비밀번호, API 키 또는 소스 코드나 IaC 템플릿에 비밀이 없습니다. 비밀 관리자를 사용하세요.

**확인**:
- 비밀번호 해싱은 적응형 알고리즘을 사용합니다(약하거나 비적응형 해싱이 아님).
- 세션 쿠키는 `Secure`, `HttpOnly` 및 `SameSite` 속성을 설정합니다.
- 로그인 엔드포인트에는 무차별 보호(잠금, 지연 또는 CAPTCHA) 기능이 있습니다.
- 소스 코드 또는 구성 파일에 하드코딩된 자격 증명이 없습니다.
- MFA는 관리자 계정에 지원됩니다.
- 세션은 로그아웃 시 무효화되고 만료가 정의됩니다.

## 규칙 보안-13: 소프트웨어 및 데이터 무결성 확인

**규칙**: 시스템은 소프트웨어와 데이터의 무결성을 확인해야 합니다.
- **역직렬화 안전성**: 신뢰할 수 없는 데이터는 검증 없이 역직렬화하면 안 됩니다. 안전한 역직렬화 라이브러리 또는 허용되는 유형의 허용 목록을 사용하세요.
- **아티팩트 무결성**: 다운로드한 종속성, 플러그인, 업데이트는 체크섬이나 디지털 서명을 통해 확인해야 합니다.
- **CI/CD 파이프라인 보안**: 빌드 파이프라인은 파이프라인 정의를 수정할 수 있는 사람을 제한해야 합니다. 코드 작성자와 배포 승인자 간의 의무는 별개입니다.
- **CDN 및 외부 리소스**: 외부 CDN에서 로드된 스크립트 또는 리소스는 SRI(하위 리소스 무결성) 해시를 사용해야 합니다.
- **데이터 무결성**: 중요한 데이터 수정은 감사 가능해야 합니다(누가 무엇을 언제 변경했는지).

**확인**:
- 신뢰할 수 없는 입력의 안전하지 않은 역직렬화 없음
- 외부 스크립트에는 CDN에서 로드될 때 SRI 무결성 속성이 포함됩니다.
- CI/CD 파이프라인 정의는 액세스가 제어되며 변경 사항은 감사 가능합니다.
- 중요한 데이터 변경 사항은 행위자, 타임스탬프 및 이전/이후 값과 함께 기록됩니다.

## 규칙 보안-14: 경고 및 모니터링

**규칙**: 로깅(SECURITY-02, SECURITY-03) 외에도 시스템에는 다음이 포함되어야 합니다.
- **보안 이벤트 알림**: 반복되는 인증 실패, 권한 에스컬레이션 시도, 비정상적인 위치에서의 액세스, 승인 실패 등 중요한 보안 이벤트에 대해 알림을 구성해야 합니다.
- **로그 무결성**: 로그는 추가 전용 또는 변조 방지 저장소에 저장되어야 합니다. 애플리케이션 코드는 자체 감사 로그를 삭제하거나 수정할 수 있어서는 안 됩니다.
- **로그 보존**: 로그는 애플리케이션의 규정 준수 요구 사항에 적합한 최소 기간 동안 보존되어야 합니다(기본값: 최소 90일).
- **모니터링 대시보드**: 주요 운영 및 보안 지표에 대해 모니터링 대시보드 또는 경보 구성을 정의해야 합니다.

**확인**:
- 인증 실패 및 승인 위반에 대한 경고가 구성됩니다.
- 애플리케이션 로그 그룹에는 보존 정책이 설정되어 있습니다(최소 90일).
- 애플리케이션 역할에는 자신의 로그 그룹/스트림을 삭제할 권한이 없습니다.
- 보안 관련 이벤트(로그인 실패, 액세스 거부, 권한 변경)로 인해 경고 생성

## 규칙 보안-15: 예외 처리 및 안전 장치 기본값

**규칙**: 모든 애플리케이션은 예외적인 조건을 안전하게 처리해야 합니다.
- **캡처 및 처리**: 모든 외부 호출(데이터베이스, API, 파일 I/O)에는 명시적인 오류 처리가 있어야 합니다. 처리되지 않은 약속 거부 또는 프로덕션에서 포착되지 않은 예외가 있어서는 안 됩니다.
- **실패 시 폐쇄됨**: 오류 발생 시 시스템은 액세스를 거부하거나 작업을 중단해야 하며 절대 실패 시 개방되지 않아야 합니다.
- **리소스 정리**: 오류 경로는 리소스(연결, 파일 핸들, 잠금)를 해제해야 합니다. try/finally, using 문 또는 동등한 패턴을 사용하세요.
- **사용자 관련 오류**: 사용자에게 표시되는 오류 메시지는 일반적이어야 하며 내부 세부정보나 시스템 정보가 없어야 합니다.
- **전역 오류 처리기**: 애플리케이션에는 처리되지 않은 예외를 포착하고 이를 기록하고(SECURITY-03에 따라) 안전한 응답을 반환하는 전역/최상위 오류 처리기가 있어야 합니다.

**확인**:
- 모든 외부 호출(DB, HTTP, 파일 I/O)에는 명시적인 오류 처리(try/catch, .catch(), 오류 콜백)가 있습니다.
- 전역 오류 처리기는 애플리케이션 진입점에서 구성됩니다.
- 오류 경로는 인증 또는 유효성 검사를 우회하지 않습니다(실패 시 닫힘).
- 오류 경로에서 리소스가 정리됩니다(연결이 닫히고 트랜잭션이 롤백됨).
- 애플리케이션 코드에서 처리되지 않은 약속 거부 또는 포착되지 않은 예외 경고가 없습니다.
