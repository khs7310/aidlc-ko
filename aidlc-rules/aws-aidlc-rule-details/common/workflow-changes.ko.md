# 작업 흐름 중간 변경 및 단계 관리

## 개요

사용자는 워크플로우 중에 실행 계획 또는 단계 실행에 대한 변경을 요청할 수 있습니다. 이 문서는 이러한 요청을 안전하고 효과적으로 처리하는 방법에 대한 지침을 제공합니다.

---

## 워크플로우 중간 변경 유형

### 1. 건너뛴 단계 추가

**시나리오**: 사용자가 원래 건너뛴 단계를 추가하려고 합니다.

**예**: "사실 해당 단계를 건너뛰었지만 사용자 스토리를 추가하고 싶습니다."

**손질**:
1. **요청 확인**: "사용자 스토리 단계를 추가하고 싶습니다. 이렇게 하면 사용자 스토리와 페르소나가 생성됩니다. 확인하시겠습니까?"
2. **종속성 확인**: 모든 필수 구성 요소 단계가 완료되었는지 확인하세요.
3. **실행 계획 업데이트**: 근거와 함께 `execution-plan.md`에 단계 추가
4. **업데이트 상태**: `aidlc-state.md`에서 단계를 "보류 중"으로 표시합니다.
5. **실행 단계**: 일반적인 단계 실행 프로세스를 따릅니다.
6. **로그 변경**: 타임스탬프와 이유가 포함된 `audit.md`의 문서

**고려사항**:
- 새로운 아티팩트의 이점을 누릴 수 있는 이후 단계를 업데이트해야 할 수도 있습니다.
- 새로운 정보를 통합하려면 기존 아티팩트를 수정해야 할 수도 있습니다.
- 타임라인이 연장됩니다

---

### 2. 계획된 단계 건너뛰기

**시나리오**: 사용자가 실행 예정인 단계를 건너뛰고 싶어 합니다.

**예**: "지금은 NFR 설계 단계를 건너뛰겠습니다."

**손질**:
1. **요청 확인**: "NFR 설계를 건너뛰고 싶습니다. 이는 NFR 패턴이나 논리적 구성 요소가 통합되지 않음을 의미합니다. 확인하시겠습니까?"
2. **영향에 대한 경고**: 누락될 내용과 잠재적인 결과를 설명합니다.
3. **명시적 확인 받기**: 사용자는 영향에 대한 이해를 명시적으로 확인해야 합니다.
4. **실행 계획 업데이트**: 이유와 함께 단계를 '건너뛰기'로 표시
5. **상태 업데이트**: `aidlc-state.md`에서 단계를 "SKIPPED"로 표시합니다.
6. **나중 단계 조정**: 나중 단계에서는 수동 설정이 필요할 수 있습니다.
7. **로그 변경**: 타임스탬프와 이유가 포함된 `audit.md`의 문서

**고려사항**:
- 이후 단계에서는 실패하거나 수동 개입이 필요할 수 있습니다.
- 사용자는 누락된 아티팩트에 대한 책임을 수락합니다.
- 필요한 경우 나중에 다시 추가할 수 있습니다.

---

### 3. 현재 스테이지 다시 시작

**시나리오**: 사용자가 현재 단계 결과에 만족하지 않아 다시 실행하고 싶어함

**예**: "이 사용자 스토리가 마음에 들지 않습니다. 다시 시작해도 될까요?"

**손질**:
1. **우려사항 이해**: "스토리에서 구체적으로 무엇을 바꾸고 싶나요?"
2. **혜택 옵션**:
   - **옵션 A**: 기존 아티팩트 수정(더 빠르게, 일부 작업 유지)
   - **옵션 B**: 완전히 다시 시작(깨끗한 상태, 추가 시간)
3. **다시 시작을 선택한 경우**:
   - 기존 아티팩트 보관: `{artifact}.backup.{timestamp}`
   - 계획 파일의 단계 확인란 재설정
   - `aidlc-state.md`에서 단계를 '진행 중'으로 표시
   - 스테이지 완료 상태 지우기
   - 처음부터 다시 실행
4. **로그 변경**: 다시 시작하는 이유와 변경 사항을 문서로 기록하세요.

**고려사항**:
- 기존 작업이 손실됩니다(단, 백업됨).
- 종속 단계를 다시 실행해야 할 수도 있음
- 타임라인이 연장됩니다

---

### 4. 이전 단계 다시 시작

**시나리오**: 사용자가 완료된 단계로 돌아가서 다시 실행하려고 합니다.

**예**: "이전에 내린 아키텍처 결정을 변경하고 싶습니다."

**손질**:
1. **영향 평가**: 다시 시작될 단계에 의존하는 모든 단계를 식별합니다.
2. **사용자 경고**: "애플리케이션 설계를 다시 시작하려면 단위 생성, 단위별 설계(모든 단위), 코드 생성 등을 다시 실행해야 합니다. 확인하시겠습니까?"
3. **명시적 확인 받기**: 사용자는 전체 영향을 이해해야 합니다.
4. **확인된 경우**:
   - 영향을 받는 모든 아티팩트를 보관합니다.
   - `aidlc-state.md`에서 영향을 받은 모든 단계를 재설정합니다.
   - 영향을 받는 모든 계획 파일의 확인란을 선택 취소하세요.
   - 다시 시작하려면 스테이지로 돌아가세요.
   - 해당 시점부터 다시 실행
5. **로그 변경**: 전체 영향 및 재시작 이유를 문서화합니다.

**고려사항**:
- 상당한 재작업 필요
- 모든 종속 단계를 다시 실행해야 합니다.
- 타임라인이 대폭 연장됩니다
- 다시 시작하는 것보다 수정하는 것이 더 나은지 고려하십시오.

---

### 5. 스테이지 깊이 변경

**시나리오**: 사용자가 현재 또는 향후 단계의 깊이 수준을 변경하려고 합니다.

**예**: "표준 대신 종합적인 요구사항 분석을 해보자"

**손질**:
1. **요청 확인**: "요구 사항 분석을 표준에서 포괄적 깊이로 변경하고 싶습니다. 이 작업은 더 철저하지만 시간이 더 오래 걸립니다. 확인하시겠습니까?"
2. **실행 계획 업데이트**: `workflow-planning.md`의 깊이 수준 변경
3. **접근 방식 조정**: 스테이지에 대한 포괄적인 깊이 지침을 따르세요.
4. **예상 업데이트**: 사용자에게 새로운 예상 일정을 알립니다.
5. **로그 변경**: 문서 깊이 변경 및 이유

**고려사항**:
- 더 많은 깊이 = 더 많은 시간, 더 나은 품질
- 깊이가 적음 = 속도는 빠르지만 세부 정보를 놓칠 수 있음
- 단계 전이나 단계 중에만 변경할 수 있으며 완료 후에는 변경할 수 없습니다.

---

### 6. 작업 흐름 일시 중지

**시나리오**: 사용자가 일시중지하고 나중에 다시 시작해야 함

**예**: "지금은 중단하고 내일 계속해야 합니다."

**손질**:
1. **현재 단계 완료**: 가능하면 현재 진행 중인 단계를 완료합니다.
2. **업데이트 체크박스**: 완료된 모든 단계를 [x]로 표시하세요.
3. **상태 업데이트**: `aidlc-state.md`이 현재 상태를 반영하는지 확인하세요.
4. **로그 일시 중지**: `audit.md`의 문서 일시 중지 지점
5. **재개 지침 제공**: "귀하가 돌아오면 기존 프로젝트를 감지하고 [현재 단계, 현재 단계]에서 계속하도록 제안하겠습니다."

**이력서**:
1. **기존 프로젝트 감지**: `aidlc-state.md` 확인
2. **컨텍스트 로드**: 완료된 단계에서 모든 아티팩트를 읽습니다.
3. **상태 표시**: 현재 단계와 다음 단계를 표시합니다.
4. **제공 옵션**: 중단된 부분부터 계속하거나 이전 작업을 검토합니다.
5. **로그 재개**: `audit.md`의 문서 재개 지점

---

### 7. 아키텍처 결정 변경

**시나리오**: 사용자가 모놀리스에서 마이크로서비스로(또는 그 반대로) 변경하기를 원합니다.

**예**: "실제로는 모놀리스 대신 마이크로서비스를 해보자"

**손질**:
1. **현재 진행 상황 평가**: 작업 흐름이 얼마나 진행되었는지 확인
2. **영향 설명**:
   - 단위 생성 이전인 경우: 영향이 최소화되고 결정만 업데이트됩니다.
   - 단위 생성 후: 단위 생성을 다시 실행해야 하며, 모든 단위별 설계
   - 코드 생성 후: 상당한 재작업이 필요한 경우
3. **권장 접근 방식**:
   - 워크플로 초기: 애플리케이션 설계 단계에서 다시 시작
   - 작업 흐름 후반: 수정이 가능한지 아니면 다시 시작할 수 있는지 고려하세요.
4. **확인 받기**: 사용자는 전체 변경 범위를 이해해야 합니다.
5. **변경 실행**: 영향을 받은 단계에 대해 다시 시작 절차를 따릅니다.

**고려사항**:
- 아키텍처 변경에는 계단식 효과가 있습니다.
- 작업 흐름 초기 = 변경이 더 쉬움
- 작업 흐름 후반부 = 비용과 이점 고려

---

### 8. 유닛 추가/제거

**시나리오**: 사용자가 단위 생성 후 단위를 추가하거나 제거하려고 합니다.

**예**: "결제 단위를 결제와 청구로 분할해야 합니다."

**손질**:
1. **영향 평가**: 어느 장치가 디자인/코드를 완료했는지 확인합니다.
2. **결과 설명**:
   - 유닛 추가: 새 유닛에 대한 전체 설계 및 코드 수행 필요
   - 유닛 제거: 다른 유닛에 기능을 재배포해야 함
   - 단위 분할: 결과 단위 모두에 대해 설계 및 코드를 다시 실행해야 함
3. **유닛 아티팩트 업데이트**:
   - `unit-of-work.md` 수정
   - `unit-of-work-dependency.md` 업데이트
   - `unit-of-work-story-map.md` 수정
4. **영향을 받는 장치 재설정**: 영향을 받는 장치를 재설계가 필요한 것으로 표시합니다.
5. **변경 사항 실행**: 영향을 받는 장치에 대한 일반적인 장치 디자인 및 코드 프로세스를 따릅니다.

**고려사항**:
- 해당 장치의 모든 다운스트림 단계에 영향을 미칩니다.
- 종속성이 변경되면 다른 장치에 영향을 미칠 수 있음
- 타임라인에 미치는 영향은 영향을 받는 장치 수에 따라 달라집니다.

## 변경 사항 처리에 대한 일반 지침

### 변경하기 전에

1. **요청 이해**: 사용자가 변경하려는 내용과 그 이유에 대해 명확한 질문을 하세요.
2. **영향 평가**: 영향을 받는 모든 단계, 아티팩트 및 종속성을 식별합니다.
3. **결과 설명**: 다시 수행해야 할 사항과 일정에 미치는 영향을 명확하게 전달합니다.
4. **대안 제공**: 때로는 다시 시작하는 것보다 수정하는 것이 더 낫습니다.
5. **명시적 확인 받기**: 사용자는 영향을 이해하고 수용해야 합니다.

### 변경 중

1. **기존 작업 보관**: 파괴적인 변경을 하기 전에 항상 백업하세요.
2. **모든 추적 업데이트**: `aidlc-state.md`, 계획 파일 및 `audit.md`을 동기화 상태로 유지
3. **진행 상황 전달**: 현재 상황을 사용자에게 지속적으로 알려주세요.
4. **변경 사항 유효성 검사**: 변경 사항이 모든 아티팩트에서 일관되게 유지되는지 확인하세요.
5. **연속성 테스트**: 변경 후에도 워크플로가 원활하게 진행될 수 있는지 확인

### 변경 후

1. **일관성 확인**: 모든 아티팩트가 변경 사항에 맞게 정렬되었는지 확인하세요.
2. **문서 업데이트**: 모든 참조가 업데이트되었는지 확인하세요.
3. **완전히 기록**: `audit.md`에 전체 변경 내역을 문서화합니다.
4. **사용자에게 확인**: 변경 사항이 사용자의 기대에 부합하는지 확인합니다.
5. **워크플로 재개**: 새 상태에서 일반 실행을 계속합니다.

## 변경 요청 결정 트리

```
User requests change
    |
    ├─ Is it current stage?
    |   ├─ Yes: Can modify or restart current stage
    |   └─ No: Go to next question
    |
    ├─ Is it a completed stage?
    |   ├─ Yes: Assess impact on dependent stages
    |   |   ├─ Low impact: Modify and update dependents
    |   |   └─ High impact: Recommend restart from that stage
    |   └─ No: Go to next question
    |
    ├─ Is it adding a skipped stage?
    |   ├─ Yes: Check prerequisites, add to plan, execute
    |   └─ No: Go to next question
    |
    ├─ Is it skipping a planned stage?
    |   ├─ Yes: Warn about impact, get confirmation, skip
    |   └─ No: Go to next question
    |
    └─ Is it changing depth level?
        ├─ Yes: Update plan, adjust approach
        └─ No: Clarify request with user
```

## 모범 사례

1. **항상 확인**: 명시적인 사용자 확인 없이는 파괴적인 변경을 수행하지 않습니다.
2. **영향 설명**: 사용자는 결정을 내리기 전에 결과를 이해해야 합니다.
3. **제안 옵션**: 변경 사항을 처리하는 방법이 여러 가지인 경우도 있습니다.
4. **보관 우선**: 파괴적인 변경을 하기 전에 항상 백업하세요.
5. **모든 항목 업데이트**: 모든 추적 파일을 동기화 상태로 유지
6. **철저히 기록**: 감사 추적을 위해 모든 변경 사항을 문서화하세요.
7. **이후 검증**: 워크플로우가 원활하게 진행될 수 있는지 확인
8. **유연성**: 워크플로는 엄격한 프로세스를 강요하지 않고 사용자 요구에 맞게 조정되어야 합니다.
