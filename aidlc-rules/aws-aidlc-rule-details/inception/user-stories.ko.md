# 사용자 스토리 - 세부 단계

## 목적
**수용 기준을 통해 요구사항을 사용자 중심 스토리로 변환**

사용자 스토리는 다음에 중점을 둡니다.
- 비즈니스 요구 사항을 사용자 중심 내러티브로 변환
- 각 스토리에 대한 명확한 승인 기준 정의
- 다양한 이해관계자 유형을 나타내는 사용자 페르소나 생성
- 팀 간 공유 이해 구축
- 구현을 위해 테스트 가능한 사양 제공

## 전제 조건
- 작업공간 감지가 완료되어야 합니다.
- 요구사항 분석 권장(가능한 경우 요구사항을 참조할 수 있음)
- 워크플로 계획에는 사용자 스토리 단계가 실행되어야 함을 나타내야 합니다.

## 지능형 평가 지침

**사용자 스토리 실행 시기**: 진행하기 전에 이 강화된 평가를 사용하세요.

### 높은 우선순위 실행(항상 실행)
- **새로운 사용자 기능**: 사용자가 직접 상호작용할 새로운 기능
- **사용자 경험 변경**: 기존 사용자 워크플로 또는 인터페이스 수정
- **다중 개인 시스템**: 다양한 유형의 사용자에게 서비스를 제공하는 애플리케이션
- **고객 지향 API**: 외부 사용자 또는 시스템이 소비하는 서비스
- **복잡한 비즈니스 로직**: 여러 시나리오 또는 비즈니스 규칙이 포함된 요구사항
- **교차 팀 프로젝트**: 여러 팀 간의 공유 이해가 필요한 작업

### 중간 우선순위 실행(복잡성 평가)
- **백엔드 사용자 영향**: 사용자 경험에 간접적으로 영향을 미치는 내부 변경 사항
- **성능 개선**: 사용자에게 표시되는 이점으로 개선
- **통합 작업**: 사용자 작업 흐름에 영향을 미치는 시스템 연결
- **데이터 변경**: 사용자 데이터, 보고서 또는 분석에 영향을 미치는 수정
- **보안 강화**: 사용자 인증 또는 권한에 영향을 미치는 변경 사항

### 복잡성 평가 요소
중간 우선순위 사례의 경우 다음 중 하나라도 해당되면 사용자 스토리를 실행하십시오.
- **범위**: 변경 사항은 여러 구성 요소 또는 사용자 터치 포인트에 걸쳐 있습니다.
- **모호함**: 요구 사항에는 스토리에서 명확하게 설명할 수 있는 불분명한 측면이 있습니다.
- **위험**: 비즈니스에 큰 영향을 미치거나 오해의 가능성이 있음
- **이해관계자**: 요구사항에 관련된 여러 비즈니스 이해관계자
- **테스트**: 사용자 승인 테스트가 필요합니다.
- **옵션**: 여러 가지 유효한 구현 접근 방식이 존재합니다.

### 간단한 경우에만 건너뛰기
- **순수한 리팩토링**: 사용자에게 영향을 주지 않는 내부 코드 개선
- **격리된 버그 수정**: 명확한 범위의 간단하고 잘 정의된 수정
- **인프라만 해당**: 사용자에게 영향을 주지 않는 변경 사항
- **개발자 도구**: 빌드 프로세스, CI/CD 또는 개발 환경 변경
- **문서**: 기능에 영향을 주지 않는 업데이트

### 기본 결정 규칙
**의심스러운 경우 사용자 스토리를 포함하고 명확한 질문을 하세요.** 적절한 설명이 포함된 포괄적인 스토리를 만드는 오버헤드는 일반적으로 다음과 같은 이점보다 큽니다.
- 보다 명확한 요구사항 이해
- 더 나은 팀 정렬
- 향상된 테스트 기준
- 이해관계자 커뮤니케이션 강화
- 구현 위험 감소
- 개발 중 비용이 많이 드는 변경 횟수 감소
- 더 나은 사용자 경험 결과

# 1부: 계획

## 1단계: 사용자 스토리에 필요한지 확인(필수)

**중요**: 사용자 스토리를 진행하기 전에 다음 평가를 수행하세요.

### 평가 프로세스
1. **요청 컨텍스트 분석**:
   - 원래 사용자 요청 및 요구 사항을 검토합니다.
   - 사용자 측 변경사항과 내부 전용 변경사항 식별
   - 작업의 복잡성과 범위를 평가합니다.
   - 비즈니스 이해관계자 참여 평가

2. **평가 기준 적용**:
   - 높은 우선순위 지표에 대한 확인(항상 실행)
   - 중간 우선순위 요소 평가(복잡성 기반 결정)
   - 건너뛰어야 하는 간단한 사례가 아닌지 확인하세요.

3. **문서 평가 결정**:
   - `aidlc-docs/inception/plans/user-stories-assessment.md` 만들기
   - 이 요청에 사용자 스토리가 중요한 이유에 대한 추론을 포함하세요.
   - 적용되는 특정 평가 기준 참조
   - 예상되는 이점 설명(명확성, 테스트, 이해관계자 조정)

4. **타당한 경우에만 진행하세요**:
   - 사용자 스토리는 프로젝트에 명확한 가치를 추가해야 합니다.
   - 평가에서는 간접비보다 구체적인 이점이 더 크다는 것을 보여야 합니다.
   - 결정은 프로젝트 이해관계자가 방어할 수 있어야 합니다.

### 평가 문서 템플릿
```markdown
# User Stories Assessment

## Request Analysis
- **Original Request**: [Brief summary]
- **User Impact**: [Direct/Indirect/None]
- **Complexity Level**: [Simple/Medium/Complex]
- **Stakeholders**: [List involved parties]

## Assessment Criteria Met
- [ ] High Priority: [List applicable criteria]
- [ ] Medium Priority: [List applicable criteria with complexity justification]
- [ ] Benefits: [Expected value from user stories]

## Decision
**Execute User Stories**: [Yes/No]
**Reasoning**: [Detailed justification]

## Expected Outcomes
- [List specific benefits user stories will provide]
- [How stories will improve project success]
```

## 2단계: 스토리 계획 만들기
- 제품 소유자의 역할을 맡습니다.
- 스토리 전개를 위한 단계별 실행 체크리스트를 통해 종합적인 계획 수립
- 각 단계와 하위 단계에는 확인란 []이 있어야 합니다.
- 요구사항을 사용자 스토리로 변환하는 방법론과 접근 방식에 중점을 둡니다.

## 3단계: 상황에 맞는 질문 생성
**지침**: 요구사항과 맥락을 철저하게 분석하여 설명을 통해 스토리 품질과 팀 이해도를 향상시킬 수 있는 모든 영역을 식별합니다. 포괄적인 사용자 스토리 개발을 보장하려면 적극적으로 질문하세요.

**중요**: 스토리 품질에 영향을 미칠 수 있는 모호하거나 세부 사항이 누락된 경우 기본적으로 질문을 합니다. 불완전하거나 불분명한 이야기를 만드는 것보다 너무 많은 질문을 하는 것이 좋습니다.

**질문 형식 지정 규칙은 `common/question-format-guide.md`을 참조하세요**

- [답변]을 사용한 질문 삽입: 태그 형식
- 모호함, 누락된 정보 또는 설명이 필요한 영역에 중점을 둡니다.
- 사용자 입력이 스토리 생성 결정을 향상시킬 수 있는 모든 곳에 질문을 생성하세요.
- **의심스러운 경우 질문하세요** - 과신은 좋지 않은 이야기로 이어집니다

**평가할 질문 카테고리**(모든 카테고리 고려):
- **사용자 페르소나** - 사용자 유형, 역할, 특성, 동기에 대해 물어보세요.
- **스토리 세분성** - 적절한 수준의 세부정보, 스토리 크기 및 분류 접근 방식에 대해 문의하세요.
- **스토리 형식** - 형식 기본 설정, 템플릿 사용 및 문서 표준에 대해 문의하세요.
- **분류 접근 방식** - 구성 방법, 우선 순위, 그룹화 전략에 대해 질문합니다.
- **수락 기준** - 세부 수준, 형식, 테스트 접근 방식 및 검증 방법에 대해 문의하세요.
- **사용자 여정** - 사용자 워크플로, 상호작용 패턴, 경험 흐름에 대해 질문하세요.
- **비즈니스 맥락** - 비즈니스 목표, 성공 지표, 이해관계자 요구 사항에 대해 물어보세요.
- **기술적 제약** - 기술적 한계, 통합 요구 사항 및 시스템 경계에 대해 문의하세요.

## 4단계: 계획에 필수 스토리 아티팩트 포함
- **항상** 스토리 계획에 다음과 같은 필수 아티팩트를 포함하세요.
  - [ ] 투자 기준에 따른 사용자 스토리로 Stories.md 생성
  - [ ] 사용자 원형 및 특성을 포함하는 personas.md 생성
  - [ ] 스토리가 독립적이고, 협상 가능하고, 가치 있고, 추정 가능하고, 작으며, 테스트 가능하도록 보장합니다.
  - [ ] 각 사례에 대한 승인 기준 포함
  - [ ] 관련 사용자 스토리에 페르소나 매핑

## 5단계: 스토리 옵션 제시
- 계획 문서에 스토리 분석을 위한 다양한 접근 방식을 포함합니다.
  - **사용자 여정 기반**: 스토리는 사용자 워크플로와 상호작용을 따릅니다.
  - **기능 기반**: 시스템 기능을 중심으로 구성된 스토리
  - **페르소나 기반**: 다양한 사용자 유형과 요구 사항에 따라 그룹화된 스토리
  - **도메인 기반**: 비즈니스 도메인 또는 컨텍스트를 중심으로 구성된 스토리
  - **에픽 기반**: 하위 스토리가 포함된 계층적 서사시로 구성된 스토리
- 각 접근 방식의 장단점과 이점을 설명합니다.
- 명확한 결정 기준으로 하이브리드 접근 방식 허용

## 6단계: 매장 스토리 계획
- 질문이 포함된 전체 스토리 계획을 `aidlc-docs/inception/plans/` 디렉토리에 저장하세요.
- 파일 이름: `story-generation-plan.md`
- 모든 [답변]: 사용자 입력용 태그 포함
- 계획이 포괄적이고 모든 스토리 개발 측면을 포괄하는지 확인하세요.

## 7단계: 사용자 입력 요청
- 스토리 계획 문서에 모든 [답변]: 태그를 직접 입력하도록 사용자에게 요청
- 감사 추적 및 결정 문서화의 중요성 강조
- [답변] 태그 작성 방법에 대한 명확한 지침을 제공하세요.
- 계속하기 전에 모든 질문에 답해야 한다고 설명합니다.

## 8단계: 답변 수집
- 사용자가 [답변]을 사용하여 모든 질문에 대한 답변을 제공할 때까지 기다립니다: 문서의 태그
- 모든 [답변]: 태그가 완료될 때까지 진행하지 마세요.
- 문서를 검토하여 [답변]이 없는지 확인하세요. 태그가 비어 있습니다.

## 9단계: 답변 분석(필수)
계속하기 전에 다음에 대한 모든 사용자 답변을 주의 깊게 검토해야 합니다.
- **모호하거나 모호한 응답**: "혼합", "어딘가 사이", "확실하지 않음", "의존적", "아마도", "아마도"
- **정의되지 않은 기준 또는 용어**: 명확한 정의가 없는 개념에 대한 언급
- **상충되는 답변**: 서로 상충되는 답변
- **생성 세부정보 누락**: 구현을 위한 구체적인 지침이 부족한 답변
- **옵션을 결합한 답변**: 명확한 결정 규칙 없이 다양한 접근 방식을 병합하는 답변
- **불완전한 설명**: 외부 요인을 정의하지 않고 참조하는 답변
- **가정 기반 응답**: 명시적으로 언급되지 않은 지식을 가정하는 답변

## 10단계: 필수 후속 질문
9단계의 분석 결과 모호한 답변이 밝혀지면 다음을 수행해야 합니다.
- [답변]을 사용하여 별도의 설명 질문 파일 만들기: 태그
- 모든 모호성이 완전히 해결될 때까지 승인을 진행하지 마십시오.
- **중요**: 철저하게 작성하세요. 불분명한 답변이 있을 때마다 후속 질문을 하세요.
- 필요한 후속 조치의 예:
  - "'A와 B의 혼합'을 언급하셨습니다. A와 B를 언제 사용할지 결정해야 하는 구체적인 기준은 무엇입니까?"
  - "'A와 B 사이'라고 말씀하셨는데요. 정확한 중간 접근 방식을 정의할 수 있나요?"
  - "'확실하지 않음'이라고 표시하셨습니다. 결정하는 데 도움이 되는 추가 정보는 무엇입니까?"
  - "'복잡성에 따라 다르다'고 말씀하셨는데, 복잡성 수준과 임계값을 어떻게 정의하시나요?"
  - "'하이브리드 접근 방식'을 선택하셨습니다. 각 방법을 언제 사용해야 하는지에 대한 구체적인 규칙은 무엇입니까?"
  - "'아마도 X'라고 말씀하셨는데요. 어떤 요인이 X를 확실히 X로 만들고 X가 아닌지를 결정하게 합니까?"
  - "당신은 '표준 관행'을 언급했습니다. 그 표준 관행이 무엇인지 정의할 수 있습니까?"

## 11단계: 구현 세부 사항 피하기
- 우선순위나 개발 업무가 아닌 스토리 창작 방법론에 집중
- 이 단계에서는 기술 세대에 대해 논의하지 마십시오.
- 개발 일정이나 스프린트 계획을 세우지 마세요.
- 스토리 구조와 형식 결정에 계속 집중하세요.

## 12단계: 승인 프롬프트 로그
- 승인을 요청하기 전에 `aidlc-docs/audit.md`에 타임스탬프가 포함된 프롬프트를 기록하세요.
