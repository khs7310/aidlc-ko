# 애플리케이션 설계 - 세부 단계

## 목적
**상위 수준의 구성 요소 식별 및 서비스 계층 설계**

애플리케이션 디자인은 다음에 중점을 둡니다.
- 주요 기능 구성요소 및 해당 책임 식별
- 구성요소 인터페이스 정의(상세한 비즈니스 로직 아님)
- 오케스트레이션을 위한 서비스 레이어 설계
- 구성요소 종속성 및 통신 패턴 설정

**참고**: 자세한 비즈니스 로직 설계는 나중에 기능 설계(단위별, 구성 단계)에서 이루어집니다.

## 전제조건
- 작업공간 감지가 완료되어야 합니다.
- 요구사항 분석 권장(기능적 컨텍스트 제공)
- 사용자 스토리 권장(사용자 스토리가 디자인 결정을 안내함)
- 실행 계획은 애플리케이션 설계 단계가 실행되어야 함을 나타내야 합니다.

## 단계별 실행

### 1. 맥락 분석
- `aidlc-docs/inception/requirements/requirements.md` 및 `aidlc-docs/inception/user-stories/stories.md` 읽기
- 주요 비즈니스 역량 및 기능 영역 식별
- 설계 범위 및 복잡성 결정

### 2. 애플리케이션 설계 계획 수립
- 애플리케이션 설계를 위한 체크박스[]를 사용하여 계획 생성
- 구성 요소, 책임, 방법, 비즈니스 규칙 및 서비스에 중점을 둡니다.
- 각 단계와 하위 단계에는 확인란 []이 있어야 합니다.

### 3. 계획에 필수 디자인 아티팩트 포함
- **항상** 디자인 계획에 다음과 같은 필수 아티팩트를 포함하세요.
  - [ ] 구성 요소 정의 및 높은 수준의 책임을 포함하여 구성 요소.md 생성
  - [ ] 메서드 시그니처를 사용하여 component-methods.md 생성(나중에 기능 설계에서 자세히 설명하는 비즈니스 규칙)
  - [ ] 서비스 정의 및 오케스트레이션 패턴을 사용하여 services.md 생성
  - [ ] 종속 관계 및 통신 패턴을 사용하여 구성 요소 종속성.md를 생성합니다.
  - [ ] 설계 완성도 및 일관성 검증

### 4. 상황에 맞는 질문 생성
**지침**: 요구 사항과 스토리를 분석하여 이 특정 애플리케이션 설계와 관련된 질문을 생성합니다. 아래 카테고리를 지침으로 활용하세요. 각 범주를 평가하고 적용 가능성이 의심스러운 경우 건너뛰지 말고 질문하십시오. 과신은 좋지 않은 결과로 이어집니다(overconfidence-prevention.md 참조).

- [답변]을 사용한 질문 삽입: 태그 형식
- 모호함, 누락된 정보 또는 설명이 필요한 영역에 중점을 둡니다.
- 사용자 입력이 디자인 결정을 향상시킬 수 있는 모든 곳에 질문을 생성하세요.
- **의심스러운 경우 질문하세요** - 과신은 잘못된 디자인으로 이어집니다.

**평가할 질문 카테고리**(모든 카테고리 고려):
- **구성요소 식별** - 구성요소 경계, 조직 및 그룹화 전략에 대해 질문합니다.
- **구성 요소 메소드** - 메소드 서명, 입력/출력 기대치 및 인터페이스 계약에 대해 질문합니다(자세한 비즈니스 규칙은 나중에 나옵니다).
- **서비스 계층 설계** - 서비스 조정, 경계, 조정 패턴에 대해 질문
- **구성요소 종속성** - 통신 패턴, 종속성 관리 및 결합 문제에 대해 문의하세요.
- **디자인 패턴** - 아키텍처 스타일 선호도, 패턴 선택, 디자인 제약 조건에 대해 물어보세요.

### 5. 스토어 애플리케이션 디자인 계획
- `aidlc-docs/inception/plans/application-design-plan.md`로 저장
- 모든 [답변]: 사용자 입력용 태그 포함
- 계획이 모든 설계 측면을 포괄하는지 확인

### 6. 사용자 입력 요청
- 사용자에게 [답변]을 작성하도록 요청: 계획 문서에서 태그를 직접 작성
- 디자인 결정의 중요성 강조
- [답변] 작성에 대한 명확한 지침 제공: 태그

### 7. 답변 수집
- 사용자가 [답변]을 사용하여 모든 질문에 대한 답변을 제공할 때까지 기다립니다: 문서의 태그
- 모든 [답변]: 태그가 완료될 때까지 진행하지 마세요.
- 문서를 검토하여 [답변]이 없는지 확인하세요. 태그가 비어 있습니다.

### 8. 답변 분석(필수)
계속하기 전에 다음에 대한 모든 사용자 답변을 주의 깊게 검토해야 합니다.
- **모호하거나 모호한 응답**: "혼합", "어느 정도", "확실하지 않음", "의존적"
- **정의되지 않은 기준 또는 용어**: 명확한 정의가 없는 개념에 대한 언급
- **상충되는 답변**: 서로 상충되는 답변
- **디자인 세부정보 누락**: 구체적인 지침이 부족한 답변
- **옵션을 결합한 답변**: 명확한 결정 규칙 없이 다양한 접근 방식을 병합하는 답변

### 9. 필수 후속 질문
8단계의 분석 결과 모호한 답변이 밝혀지면 다음을 수행해야 합니다.
- [답변]을 사용하여 계획 문서에 구체적인 후속 질문을 추가하세요. 태그
- 모든 모호성이 해결될 때까지 승인을 진행하지 마십시오.
- 필요한 후속 조치의 예:
  - "'A와 B의 혼합'을 언급하셨습니다. A와 B를 언제 사용할지 결정해야 하는 구체적인 기준은 무엇입니까?"
  - "'A와 B 사이'라고 말씀하셨는데요. 정확한 중간 접근 방식을 정의할 수 있나요?"
  - "'확실하지 않음'이라고 표시하셨습니다. 결정하는 데 도움이 되는 추가 정보는 무엇입니까?"
  - "'복잡성에 따라 다르다'고 말씀하셨는데요. 복잡성 수준을 어떻게 정의하시나요?"

### 10. 애플리케이션 디자인 아티팩트 생성
- 승인된 계획을 실행하여 디자인 결과물 생성
- 다음을 사용하여 `aidlc-docs/inception/application-design/components.md`을(를) 만듭니다.
  - 구성요소 이름 및 목적
  - 구성요소 책임
  - 구성요소 인터페이스
- 다음을 사용하여 `aidlc-docs/inception/application-design/component-methods.md`을(를) 만듭니다.
  - 각 구성 요소의 메서드 서명
  - 각 방법의 대략적인 목적
  - 입력/출력 유형
  - 참고: 자세한 비즈니스 규칙은 기능 설계(단위별, 구성 단계)에서 정의됩니다.
- 다음을 사용하여 `aidlc-docs/inception/application-design/services.md`을(를) 만듭니다.
  - 서비스 정의
  - 서비스 책임
  - 서비스 상호 작용 및 오케스트레이션
- 다음을 사용하여 `aidlc-docs/inception/application-design/component-dependency.md`을(를) 만듭니다.
  - 관계를 보여주는 종속성 매트릭스
  - 구성요소 간 통신 패턴
  - 데이터 흐름 다이어그램
- 위에서 만든 여러 디자인 문서를 하나의 문서로 통합하는 `aidlc-docs/inception/application-design/application-design.md`을(를) 만듭니다.
