# 요구사항 분석(적응형)

**제품 소유자의 역할을 맡습니다**

**적응 단계**: 항상 실행됩니다. 세부 수준은 문제의 복잡성에 맞춰 조정됩니다.

**적응형 깊이 설명은 [깊이 레벨.md](../common/depth-levels.md)를 참조하세요**

## 전제조건
- 작업공간 감지가 완료되어야 합니다.
- 리버스 엔지니어링을 완료해야 합니다(브라운필드인 경우).

## 실행 단계

### 1단계: 리버스 엔지니어링 컨텍스트 로드(사용 가능한 경우)

**브라운필드 프로젝트인 경우**:
- `aidlc-docs/inception/reverse-engineering/architecture.md` 로드
- `aidlc-docs/inception/reverse-engineering/component-inventory.md` 로드
- `aidlc-docs/inception/reverse-engineering/technology-stack.md` 로드
- 요청을 분석할 때 이를 사용하여 기존 시스템을 이해합니다.

### 2단계: 사용자 요청 분석(의도 분석)

#### 2.1 명확성 요청
- **명확함**: 구체적이고 잘 정의되어 있으며 실행 가능함
- **모호함**: 일반적이고 모호하며 설명이 필요함
- **불완전**: 주요 정보가 누락되었습니다.

#### 2.2 요청 유형
- **새로운 기능**: 새로운 기능 추가
- **버그 수정**: 기존 문제 수정
- **리팩토링**: 코드 구조 개선
- **업그레이드**: 종속성 또는 프레임워크 업데이트
- **마이그레이션**: 다른 기술로 이동
- **개선사항**: 기존 기능 개선
- **새 프로젝트**: 처음부터 시작하기

#### 2.3 초기 범위 추정
- **단일 파일**: 하나의 파일로 변경됩니다.
- **단일 구성 요소**: 하나의 구성 요소/패키지로 변경
- **다중 구성요소**: 여러 구성요소에 걸친 변경사항
- **시스템 전체**: 전체 시스템에 영향을 미치는 변경사항
- **교차 시스템**: 여러 시스템에 영향을 미치는 변경사항

#### 2.4 초기 복잡도 추정
- **사소한**: 간단하고 직접적인 변경
- **간단함**: 명확한 구현 경로
- **보통**: 약간의 복잡성, 다양한 고려 사항
- **복잡함**: 상당한 복잡성, 많은 고려 사항

### 3단계: 요구사항 깊이 결정

**요청 분석을 기반으로 깊이를 결정합니다.**

**최소 깊이** - 다음과 같은 경우에 사용하세요.
- 요청은 명확하고 간단합니다.
- 자세한 요구사항은 필요하지 않습니다.
- 기본적인 이해를 문서화하세요.

**표준 깊이** - 다음 경우에 사용:
- 요청에 설명이 필요함
- 필요한 기능적 및 비기능적 요구사항
- 정상적인 복잡성

**포괄적인 깊이** - 다음과 같은 경우에 사용하세요.
- 여러 이해관계자가 참여하는 복잡한 프로젝트
- 위험도가 높거나 중요한 시스템
- 추적성이 필요한 세부 요구사항

### 4단계: 현재 요구 사항 평가

사용자가 제공한 모든 것을 분석합니다.
   - 의도 진술 또는 설명(이미 audit.md에 로그인되어 있음)
   - 기존 요구사항 문서(언급된 경우 검색 작업공간)
   - 붙여넣은 콘텐츠 또는 파일 참조
   - 마크다운이 아닌 문서를 마크다운 형식으로 변환

### 5단계: 철저한 완전성 분석

**중요**: 포괄적인 분석을 사용하여 요구사항 완전성을 평가합니다. 모호하거나 세부 사항이 누락된 경우 기본적으로 질문을 합니다.

**필수**: 다음 영역을 모두 평가하고 불분명한 부분에 대해 질문하세요.
- **기능 요구 사항**: 핵심 기능, 사용자 상호 작용, 시스템 동작
- **비기능적 요구사항**: 성능, 보안, 확장성, 유용성
- **사용자 시나리오**: 사용 사례, 사용자 여정, 엣지 사례, 오류 시나리오
- **비즈니스 컨텍스트**: 목표, 제약 조건, 성공 기준, 이해관계자 요구
- **기술적 맥락**: 통합 지점, 데이터 요구 사항, 시스템 경계
- **품질 속성**: 신뢰성, 유지 관리 가능성, 테스트 가능성, 접근성

**의심스러운 경우 질문하세요** - 불완전한 요구사항으로 인해 구현이 제대로 이루어지지 않습니다.

### 5.1단계: 확장 옵트인 프롬프트

**필수**: `## Opt-In Prompt` 섹션에 대해 로드된 모든 `*.opt-in.md` 파일(워크플로 시작 시 `extensions/` 하위 디렉터리에서 로드됨)을 검색합니다. 확장 프로그램을 선언하는 각 확장 프로그램에 대해 6단계에서 생성된 명확한 질문 파일에 해당 질문을 포함합니다. 각 선택 질문을 사용자 대화와 동일한 언어로 제시합니다.

답변을 받은 후:
1. `## Extension Configuration` 아래의 `aidlc-docs/aidlc-state.md`에 각 확장 프로그램의 활성화 상태를 기록합니다.

```markdown
## Extension Configuration
| Extension | Enabled | Decided At |
|---|---|---|
| [Extension Name] | [Yes/No] | Requirements Analysis |
```

2. **지연된 규칙 로드**: 사용자가 선택한 각 확장 프로그램에 대해 지금 전체 규칙 파일을 로드합니다. 규칙 파일은 명명 규칙에 따라 파생됩니다. 즉, 선택 파일 이름에서 `.opt-in.md`을 제거하고 `.md`을 추가합니다(예: `security-baseline.opt-in.md` → `security-baseline.md`). 사용자가 선택 해제한 확장의 경우 전체 규칙 파일을 로드하지 마세요.

### 6단계: 명확한 질문 생성(선제적 접근 방식)
   - **항상** 요구사항이 특별히 명확하고 완전하지 않은 한 `aidlc-docs/inception/requirements/requirement-verification-questions.md`을(를) 생성하세요.
   - 누락되었거나 불분명하거나 모호한 영역에 대해 질문하세요.
   - 기능적 요구사항, 비기능적 요구사항, 사용자 시나리오 및 비즈니스 컨텍스트에 중점을 둡니다.
   - 사용자에게 모든 [답변]: 태그를 질문 문서에 직접 입력하도록 요청
   - 답변에 대한 객관식 옵션을 제시하는 경우:
     - 옵션에 A, B, C, D 등의 라벨을 붙입니다.
     - 옵션이 상호 배타적이고 중복되지 않는지 확인하세요.
     - 항상 사용자 정의 응답 옵션을 포함하십시오: "X) 기타([답변] 뒤에 설명하십시오: 아래 태그)"
   - 문서에서 사용자 답변을 기다립니다.
   - **필수**: 모호성에 대한 모든 답변을 분석하고 필요한 경우 후속 질문을 만듭니다.
   - **필수**: 모든 모호성이 해결되거나 사용자가 명시적으로 진행을 요청할 때까지 계속 질문하세요.

### ⛔ GATE: 사용자 답변을 기다립니다
요구사항-검증-질문.md의 모든 질문에 답변하고 검증될 때까지 7단계로 진행하지 마십시오.
사용자에게 질문 파일을 제시하고 중지합니다.

### 7단계: 요구사항 문서 생성
   - **전제 조건**: 6단계 게이트를 통과해야 합니다. 모든 답변을 받고 분석합니다.
   - `aidlc-docs/inception/requirements/requirements.md` 만들기
   - 상단에 의도 분석 요약을 포함합니다.
     - 사용자 요청
     - 요청 유형
     - 범위 추정
     - 복잡성 추정
   - 기능적 요구사항과 비기능적 요구사항을 모두 포함
   - 질문을 명확히 하기 위해 사용자의 답변을 통합합니다.
   - 주요 요구 사항에 대한 간략한 요약 제공

### 8단계: 상태 추적 업데이트

`aidlc-docs/aidlc-state.md` 업데이트:

```markdown
## Stage Progress
### 🔵 INCEPTION PHASE
- [x] Workspace Detection
- [x] Reverse Engineering (if applicable)
- [x] Requirements Analysis
```

### 9단계: 기록 및 진행
   - `aidlc-docs/audit.md`의 타임스탬프가 포함된 로그 승인 프롬프트
   - 다음 구조에 완료 메시지가 표시됩니다.
     1. **완료 알림**(필수): 항상 다음으로 시작하세요.

```markdown
# 🔍 Requirements Analysis Complete
```

     2. **AI 요약**(선택사항): 요구사항에 대한 구조화된 핵심 요약을 제공합니다.
        - 형식: "요구사항 분석에서 [프로젝트 유형/복잡성]이 확인되었습니다:"
        - 주요 기능 요구 사항 나열(글머리 기호)
        - 주요 비기능적 요구사항 나열(글머리 기호)
        - 해당되는 경우 아키텍처 고려 사항이나 기술 결정을 언급합니다.
        - 워크플로 지침을 포함하지 마세요("검토해 주세요", "알려주세요", "다음 단계로 진행하세요", "진행하기 전에").
        - 사실에 기반하고 내용 중심을 유지하세요.
     3. **형식화된 워크플로 메시지**(필수): 항상 다음과 같은 정확한 형식으로 끝납니다.

```markdown
> **📋 <u>**REVIEW REQUIRED:**</u>**  
> Please examine the requirements document at: `aidlc-docs/inception/requirements/requirements.md`



> **🚀 <u>**WHAT'S NEXT?**</u>**
>
> **You may:**
>
> 🔧 **Request Changes** -  Ask for modifications to the requirements if required based on your review 
> [IF User Stories will be skipped, add this option:]
> 📝 **Add User Stories** - Choose to Include **User Stories** stage (currently skipped based on project simplicity)  
> ✅ **Approve & Continue** - Approve requirements and proceed to **[User Stories/Workflow Planning]**

---
```

   - 계속하기 전에 명시적인 사용자 승인을 기다리십시오.
   - 타임스탬프를 사용하여 승인 응답 기록
   - aidlc-state.md에서 요구사항 분석 단계 업데이트 완료
