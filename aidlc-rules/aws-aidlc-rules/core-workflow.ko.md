# 우선순위: 이 워크플로는 다른 모든 기본 제공 워크플로보다 우선합니다.
# 사용자가 소프트웨어 개발을 요청하면 항상 이 워크플로를 먼저 따르세요.

## 적응형 워크플로 원리
**워크플로는 작업에 맞춰 조정되며 그 반대는 아닙니다.**

AI 모델은 다음을 기반으로 어떤 단계가 필요한지 지능적으로 평가합니다.
1. 사용자가 명시한 의도와 명확성
2. 기존 코드베이스 상태(있는 경우)
3. 복잡성과 변경 범위
4. 위험 및 영향 평가

## 필수: 규칙 세부정보 로드
**중요**: 모든 단계를 수행할 때 규칙 세부 정보 파일에서 관련 콘텐츠를 읽고 사용해야 합니다. 사용된 IDE 또는 설정 방법에 관계없이 이러한 경로를 순서대로 확인하고 존재하는 첫 번째 경로를 사용하십시오.
- `.aidlc/aidlc-rules/aws-aidlc-rule-details/`(일반적으로 AI 지원 설정)
- `.aidlc-rule-details/`(Cursor, Cline, Claude Code, GitHub Copilot, OpenAI Codex에서 일반적)
- `.kiro/aws-aidlc-rule-details/`(Kiro IDE 및 CLI에서 일반적)
- `.amazonq/aws-aidlc-rule-details/`(Amazon Q Developer의 경우 일반적)

모든 후속 규칙 세부 정보 파일 참조(예: `common/process-overview.md`, `inception/workspace-detection.md`)는 위에서 확인된 규칙 세부 정보 디렉터리를 기준으로 합니다.

**공통 규칙**: 워크플로 시작 시 항상 공통 규칙을 로드합니다.
- 작업 흐름 개요를 보려면 `common/process-overview.md` 로드
- 세션 재개 안내를 위해 `common/session-continuity.md` 로드
- 콘텐츠 유효성 검사 요구 사항을 위해 `common/content-validation.md` 로드
- 질문 형식 지정 규칙에 대한 `common/question-format-guide.md` 로드
- 워크플로 실행 전반에 걸쳐 이를 참조하세요.

## 필수: 확장 프로그램 로드(컨텍스트 최적화)
**중요**: 워크플로 시작 시 `extensions/` 디렉터리를 재귀적으로 스캔하되 전체 규칙 파일이 아닌 경량 옵트인 파일만 로드하세요. 사용자가 선택한 후 요청 시 전체 규칙 파일이 로드됩니다.

**로드 프로세스**:
1. `extensions/` 아래의 모든 하위 디렉터리를 나열합니다(예: `extensions/security/`, `extensions/compliance/`).
2. 각 하위 디렉터리에서 `*.opt-in.md` 파일만 로드하세요. 이 파일에는 확장 프로그램의 선택 프롬프트가 포함되어 있습니다. 해당 규칙 파일은 규칙에 따라 파생됩니다. `.opt-in.md` 접미사를 제거하고 `.md`를 추가합니다(예: `security-baseline.opt-in.md` → `security-baseline.md`).
3. 이 단계에서는 전체 규칙 파일(예: `security-baseline.md`)을 로드하지 마세요.

**지연된 규칙 로드**:
- 요구 사항 분석 중에 로드된 `*.opt-in.md` 파일의 선택 프롬프트가 사용자에게 표시됩니다.
- 사용자가 확장에 대해 IN을 선택하면 해당 지점에서 해당 규칙 파일(명명 규칙에 따라 파생됨)을 로드합니다.
- 사용자가 옵트아웃하면 전체 규칙 파일이 로드되지 않습니다. 즉, 컨텍스트가 저장됩니다.
- 일치하는 `*.opt-in.md` 파일이 없는 확장은 항상 적용됩니다. 워크플로 시작 시 즉시 규칙 파일을 로드합니다.

**시행**(로드/활성화된 확장에만 적용):
- 확장 규칙은 선택적 지침이 아닌 엄격한 제약 조건입니다.
- 각 단계에서 모델은 단계의 목적, 생성되는 아티팩트 및 작업의 컨텍스트를 기반으로 적용 가능한 확장 규칙을 지능적으로 평가하고 관련 있는 규칙만 시행합니다.
- 현재 단계에 적용되지 않는 규칙은 규정 준수 요약에 N/A로 표시되어야 합니다. (이는 차단 결과가 아닙니다.)
- 적용 가능한 활성화된 확장 규칙을 준수하지 않으면 **차단 결과**입니다. 해결될 때까지 단계 완료를 표시하지 않습니다.
- 단계 완료를 제시할 때 확장 규칙 준수 요약(규칙당 준수/비준수/N/A, N/A 결정에 대한 간략한 근거 포함)을 포함합니다.

**조건부 적용**: 확장 프로그램은 조건부로 활성화/비활성화될 수 있습니다. 선택 메커니즘은 `inception/requirements-analysis.md`을 참조하세요. 어떤 단계에서든 연장을 시행하기 전에 `## Extension Configuration` 아래의 `aidlc-docs/aidlc-state.md`에서 `Enabled` 상태를 확인하세요. 비활성화된 확장을 건너뛰고 audit.md에 건너뛰기를 기록합니다. 구성이 없으면 기본값은 강제로 적용됩니다.

## 필수: 콘텐츠 검증
**중요**: 파일을 생성하기 전에 `common/content-validation.md` 규칙에 따라 콘텐츠의 유효성을 검사해야 합니다.
- Mermaid 다이어그램 구문 검증
- ASCII 아트 다이어그램 유효성 검사(`common/ascii-diagram-standards.md` 참조)
- 특수 문자를 올바르게 이스케이프 처리하세요
- 복잡한 시각적 콘텐츠에 대한 대체 텍스트 제공
- 콘텐츠 구문 분석 호환성 테스트

## 필수: 질문 파일 형식
**중요**: 어떤 단계에서든 질문을 할 때는 질문 형식 지침을 따라야 합니다.

**다음을 포함한 전체 질문 형식 규칙은 `common/question-format-guide.md`을 참조하세요**
- 객관식 형식(A, B, C, D, E 옵션)
- [답변]: 태그 사용법
- 답변 검증 및 모호성 해결

## 필수: 맞춤 환영 메시지
**중요**: 소프트웨어 개발 요청을 시작할 때 환영 메시지를 표시해야 합니다.

**환영 메시지 표시 방법**:
1. `common/welcome-message.md`(해결된 규칙 세부정보 디렉터리)에서 환영 메시지를 로드합니다.
2. 사용자에게 전체 메시지를 표시합니다.
3. 이 작업은 새 워크플로 시작 시 한 번만 수행해야 합니다.
4. 컨텍스트 공간을 절약하기 위해 후속 상호 작용에서 이 파일을 로드하지 마십시오.

- 단위 생성(조건부)

## 작업공간 감지(항상 실행)

1. **필수**: 전체 원시 입력을 사용하여 audit.md에 초기 사용자 요청을 기록합니다.
2. `inception/workspace-detection.md`에서 모든 단계 로드
3. 작업 공간 감지 실행:
   - 기존aidlc-state.md를 확인합니다(발견된 경우 재개).
   - 기존 코드에 대한 작업 공간 스캔
   - 브라운필드인지 그린필드인지 확인
   - 기존 리버스 엔지니어링 아티팩트 확인
4. 다음 단계 결정: 리버스 엔지니어링(브라운필드이고 아티팩트가 없는 경우) 또는 요구 사항 분석
5. **필수**: audit.md의 결과 기록
6. 사용자에게 완료 메시지 표시(메시지 형식은 작업 공간 감지.md 참조)
7. 자동으로 다음 단계로 진행

## 리버스 엔지니어링(조건부 - 브라운필드만 해당)

**다음 경우에 실행**:
- 기존 코드베이스가 감지되었습니다.
- 이전 리버스 엔지니어링 아티팩트가 발견되지 않았습니다.

**다음인 경우 건너뛰기**:
- 그린필드 프로젝트
- 이전 리버스 엔지니어링 아티팩트가 존재합니다.

**실행**:
1. **필수**: audit.md에서 리버스 엔지니어링 로그 시작
2. `inception/reverse-engineering.md`에서 모든 단계 로드
3. 리버스 엔지니어링을 실행합니다.
   - 모든 패키지 및 구성요소 분석
   - 비즈니스 거래를 포괄하는 전체 시스템에 대한 비즈니스 개요를 생성합니다.
   - 아키텍처 문서 생성
   - 코드 구조 문서 생성
   - API 문서 생성
   - 구성요소 인벤토리 생성
   - 구성 요소 전반에 걸쳐 비즈니스 트랜잭션이 구현되는 방식을 설명하는 상호 작용 다이어그램 생성
   - 기술 스택 문서 생성
   - 종속성 문서 생성

4. **명시적 승인 대기**: 자세한 완료 메시지 표시(메시지 형식은 reverse-engineering.md 참조) - 사용자가 확인할 때까지 진행하지 마세요.
5. **필수**: 전체 원시 입력을 사용하여 audit.md에 사용자 응답을 기록합니다.

## 요구사항 분석(항상 실행 - 적응형 깊이)

**항상 실행**되지만 깊이는 요청의 명확성과 복잡성에 따라 달라집니다.
- **최소**: 간단하고 명확한 요청 - 문서 의도 분석만 가능
- **표준**: 일반적인 복잡성 - 기능적 및 비기능적 요구 사항 수집
- **포괄적**: 복잡하고 위험도가 높으며 추적이 가능한 세부 요구사항

**실행**:
1. **필수**: 이 단계에서 audit.md에 모든 사용자 입력을 기록합니다.
2. `inception/requirements-analysis.md`에서 모든 단계 로드
3. 요구사항 분석 실행:
   - 리버스 엔지니어링 아티팩트 로드(브라운필드인 경우)
   - 사용자 요청 분석(의도 분석)
   - 필요한 요구사항 깊이 결정
   - 현재 요구 사항 평가
   - 명확한 질문을 하세요(필요한 경우)
   - 요구사항 문서 생성
4. 적절한 깊이(최소/표준/종합)에서 실행
5. **명시적 승인을 기다립니다**: 요구사항-analytics.md 세부 단계의 승인 형식을 따르세요. 사용자가 확인할 때까지 진행하지 마세요.
6. **필수**: 전체 원시 입력을 사용하여 audit.md에 사용자 응답을 기록합니다.

## 사용자 스토리(조건부)

**지능형 평가**: 다단계 분석을 사용하여 사용자 스토리가 가치를 더하는지 확인합니다.

**항상 IF를 실행**(우선순위 지표):
- 새로운 사용자 대상 기능
- 사용자 워크플로 또는 상호 작용에 영향을 미치는 변경 사항
- 다양한 사용자 유형 또는 페르소나가 관련됨
- 승인 기준이 필요한 복잡한 비즈니스 요구사항
- 부서간 팀 협업이 필요함
- 고객 대상 API 또는 서비스 변경 사항
- 새로운 제품 기능 또는 개선 사항

**IF 실행 가능성 있음**(중간 우선 순위 - 복잡성 평가):
- 기존 사용자 대상 기능 수정
- 사용자 경험에 간접적으로 영향을 미치는 백엔드 변경 사항
- 사용자 워크플로우에 영향을 미치는 통합 작업
- 사용자가 확인할 수 있는 이점으로 성능 개선
- 사용자 상호 작용에 영향을 미치는 보안 강화
- 사용자 데이터 또는 보고서에 영향을 미치는 데이터 모델 변경

**복잡성 기반 평가**: 우선순위가 중간인 경우 다음과 같은 경우 사용자 스토리를 실행합니다.
- 요청에 여러 구성요소 또는 서비스가 포함됩니다.
- 여러 사용자 터치포인트에 걸쳐 변경사항이 적용됩니다.
- 비즈니스 논리가 복잡하거나 여러 시나리오가 있음
- 요구 사항에는 이야기를 통해 명확해질 수 있는 모호성이 있습니다.
- 구현은 여러 사용자 여정에 영향을 미칩니다
- 변화가 비즈니스에 상당한 영향을 미치거나 위험을 초래함

**다음의 경우에만 건너뛰세요**(낮은 우선순위 - 단순 사례):
- 사용자에게 영향을 주지 않는 순수한 내부 리팩토링
- 명확하고 격리된 범위의 간단한 버그 수정
- 사용자에게 영향을 주지 않는 인프라 변경
- 기능 변경 없이 기술 부채 정리
- 개발자 도구 또는 빌드 프로세스 개선
- 문서 전용 업데이트

**평가 기준**: 의심스러운 경우 다음에 대한 사용자 스토리를 포함하는 것이 좋습니다.
- 사업 이해관계자 참여 요청
- 사용자 승인 테스트가 필요한 변경 사항
- 다양한 구현 접근 방식을 갖춘 기능
- 팀 공유에 대한 이해가 도움이 되는 업무
- 요구사항의 명확성이 중요한 프로젝트

**평가 과정**:
1. 요청 복잡성 및 범위 분석
2. 사용자 영향 식별(직접 또는 간접)
3. 비즈니스 상황과 이해관계자 요구 사항을 평가합니다.
4. 팀 협업 이점 고려
5. 경계선 케이스에는 기본적으로 포함됩니다.

**참고**: 요구사항 분석이 실행되면 스토리는 해당 요구사항을 참조하고 구축할 수 있습니다.

**사용자 스토리는 한 단계 내에 두 부분으로 구성됩니다**:
